Hackers Use Compromised ConnectWise Credential to Sign In to 173 Microsoft 365 Tenants

news The Hacker News · 2026-10-17 · ↗ original

Cybersecurity researchers are sounding the alarm related to an active campaign in which unknown threat actors are abusing a compromised Microsoft 365 (M365) credential belonging to ConnectWise Cloud Backup (formerly SkyKick) to gain unauthorized access to customers' M365 environments.

ConnectWise Cloud Backup is a cloud-based backup and recovery service built for managed service providers (MSPs) to secure their clients' Microsoft 365 or Google Workspace data. To accomplish its tasks, the application is granted broad access to mailboxes, OneDrive, SharePoint, Teams, and directory data in every tenant on which it's installed.

Huntress said it has observed confirmed unauthorized sign-ins within 173 partner/customer tenants using the compromised vendor credential. The incident impacts every organization that has the app installed, and the credential works against every tenant the app is consented in.

"The app's credential is in hostile hands," security researcher Jonathan Semon said. "It was used to obtain Microsoft Graph tokens in customer tenants from 144.172.64[.]128 on October 15, between 06:13 and 08:34 UTC. The actor moved through tenants in sorted GUID order, a few seconds apart, which points to a script working from a target list."

In the observed attackers, the adversary has been observed authenticating to the app using their own tooling, in a manner analogous to the backup service, and obtains tokens with the app's existing permissions. Given that the app has extensive permissions to access customer data, an attacker in possession of the tokens can read mailboxes, files, and directory data the backup service can.

Huntress said the same IP address engaged in password spraying against four law firm tenants on October 13 and 14, 2026, although it said it detected no successful user sign-ins in its telemetry.

In at least one partner tenant, the cybersecurity company said it found a separate ConnectWise app assigning itself Global Administrator privileges and adding credentials to other trusted applications within this environment, thereby opening a pathway to other privileged apps within customer environments. This effectively extends the risk beyond the vendor account.

"The ConnectWise Cloud Management app for Microsoft Teams (application ID 24205314-2b89-4e07-a2a4-579e898a5640) added itself to the Global Administrator role, then ran a Python script (User-Agent Python-urllib/3.12) that modified two other applications in the tenant: an MSP management application, and Huntress's own application (Huntress Security Platform), adding new client secrets to both," Semon explained.

"The two applications that received new secrets are trusted, privileged tools. Adding a credential to an MSP management application can extend access beyond the one tenant, because those applications are often consented into the MSP's customers' tenants. A credential on a security tool's application gives the holder whatever that tool is permitted to do."

Todyl, in a similar analysis, said it detected an unauthorized party authenticating to Microsoft Graph as the ConnectWise Cloud Backup application.

"The access inherited the app's existing consent, which permits read/write access to mail and attachments (full mailbox access through Exchange Web Services), OneDrive and SharePoint files, and Teams chats, including the ability to restore data," Nicholas Koken, Todyl's head of Detection Engineering, said.

"Revoking user sessions does not end this access. Disabling the app in a tenant stops new tokens from being issued there, though tokens already issued stay valid for up to 90 minutes. Any tenant where the app is still enabled stays exposed until ConnectWise rotates the credential."

In response to the incident, ConnectWise has taken the step of closing Cloud Backup application access until further notice. The company said it has found no evidence that Cloud Backup partner backup data has been compromised. It has also shared the following indicators of compromise -

  • In the Microsoft Entra Admin Center, navigate to Monitoring → Sign-in logs, select the Service principal sign-ins tab, and filter by Application ID 506e08f9-6e9a-4da4-942b-a099a03644ae.
  • The default User sign-ins tab will not display the required information.
  • In the IP address column, review authentication activity originating from IP addresses outside expected Microsoft/Azure ranges. The application's normal egress has been identified as Azure private IPv6.
  • Suspicious IP address: 144.172.64[.]128

"The backup service needs broad access to do its job, and an attacker using its credentials will inherit that level of access for every tenant where the app is installed," Huntress explained.

"Depending on the permissions in the tenant, that can include mailboxes, OneDrive and SharePoint files, Teams data, and directory information, much of it belonging to your clients. Some of that access, such as directory reads through Microsoft Graph, leaves no audit trail, which is why we suggest acting now instead of waiting for proof of access. The full potential impact depends on the permissions in play in each tenant."

Users are recommended to disable the application until ConnectWise confirms all credentials have been reset, enable Microsoft Graph activity logs, audit for any new credentials added since October 13, 2026, and check Entra audit logs for ConnectWise or SkyKick applications adding themselves to a directory role.

The development comes as Google's Mandiant and Google Threat Intelligence Group, along with ManageEngine Threat Analysis Lab, detailed an "ephemeral supply chain tampering" of the update infrastructure belonging to AOMEI Backupper, a data backup, disk cloning, and disaster recovery software, to bypass traditional security defenses and deliver malware such as CROSSROAD and SHINYROAD.

"The threat actor conducted repeated, short-burst configuration tampering against AOMEI origin servers," Google said. "Each tampering window remained active for only five to ten minutes before reverting to authentic versions. During the brief tampering windows, the threat actor modified the update settings file on the update server to redirect the software to download a malicious ZIP package from attacker-controlled servers instead of legitimate updates."

The ZIP archive contains CROSSROAD, an initial downloader responsible for environment validation and staging follow-on payloads. It's also designed to establish scheduled task-based persistence to deploy SHINYROAD, a modular backdoor framework for covert command-and-control, via DLL sideloading.

The software supply chain compromise campaign, which occurred between April and July 2026, has been attributed to a previously undocumented threat cluster codenamed UNC7017. The activity marks the first time that such a compromise has played out in brief intervals instead of maintaining a persistent, static modification on the servers.

The campaign is assessed to have impacted organizations spanning a wide range of sectors, including IT services, telecommunications, higher education, and related entities in Australia, Brazil, India, Pakistan, Portugal, Singapore, South Africa, Spain, Switzerland, Türkiye, and the U.S.

Critical BlockStrap flaw lets hackers run code on Magento servers

news BleepingComputer · 2026-10-16 · ↗ original

Researchers warn that hackers could soon exploit a maximum-severity vulnerability (CVE-2026-103849) affecting Magento and Adobe Commerce, potentially allowing them to execute arbitrary PHP code on store servers.

According to e-commerce security firm Sansec, attacks leveraging the vulnerability, dubbed BlockStrap, have not yet been observed, but threat actors are expected to find a way to exploit it.

The researchers based their assessment on identifying four potential attack paths involving CVE-2026-103849 in less than 24 hours.

The flaw impacts September versions of Adobe Commerce and Magento Open Source through 2.4.9 and Adobe Commerce B2B through 1.5.3.

The security firm warned that Adobe’s “priority 2” rating of this flaw does not reflect the danger and urgency in this case, despite the more complex attack path.

“The attack path is complex, but anyone with an AI agent can reverse-engineer the patch into working exploits in a relatively short time,” stated Sansec states.

“That is why we question Adobe's priority 2 rating (patch within 30 days). StyleSmuggler went from a priority 1 hotfix to mass exploitation in three days, and BlockStrap is of similar complexity.”

Adobe’s bulletin, published on October 13, describes the flaw as an improper neutralization of special elements used in a template engine, leading to arbitrary code execution.

Sansec explains that BlockStrap is a second-pass template engine directive injection that allows attacker-controlled content in a child email template to be signed and processed again at the root level, executing a smuggled {{block}} directive.

According to Sansec’s analysis, BlockStrap exposes a gap left by the StyleSmuggler fix in the same email-template engine.

Adobe’s fix replaces the generic processing with registered placeholders, preventing exploitation.

Sansec says that a plain Composer install isn’t enough to address the risk, and website administrators must apply the 2026-oct release or Adobe’s isolated patch.

“BlockStrap and StyleSmuggler are separate fixes. You need both, so keep the September VULN-39341 hotfix in place as well,” Sansec cautions.

The e-commerce security company says it will provide an update when it detects mass attack waves, which it expects to occur soon.

Fake Claude, ChatGPT Attacks Surge, Putting Developers at Risk

news Dark Reading · 2026-10-16 · ↗ original

The Internet is littered with convincing counterfeit AI offerings that, instead of providing popular tools, drop infostealers, remote access Trojans (RATs), and other threats inside enterprise networks.

In a report this week, Any.Run researchers examined threat campaigns that use AI-themed lures that impersonate leading brands such as Claude, ChatGPT, and others. Over a six-month period, a full 1,258 incidents analyzed on the firm's platform traced back to fake AI tool attacks.

The lures were presented in a variety of ways, from SEO poisoning and malicious ads to fake download pages and AI-themed artifacts. The campaigns most often impersonated Anthropic's Claude, with 60% of the analyses, and OpenAI's ChatGPT and Codex representing 33% of the analyses. Any.Run researchers also found the attacks frequently used a familiar tactic.

"The attacks share one trait: the employee performs the decisive step. They paste an 'install command,' run a convincing installer, or sign in to a fake window," the report stated. "That can put source code, cloud and AI API keys, active business sessions, ad accounts, and billing access at risk, turning a single user action into potential data exposure, account compromise, financial loss, or disruption to development and marketing operations."

The 1,258 analyses indicate these types of attacks are on the rise, according to Any.Run's research team.

"This number alone shows how widespread the problem has become, especially considering that security teams from over 16,000 companies worldwide use Any.Run to investigate suspicious activity," a research team spokesperson tells Dark Reading. "While it's impossible to confirm the exact number of infections, the data suggests these campaigns reached a significant number of users."

ClickFix, InstallFix & AI-Themed Lures

Any.Run's report showed that ClickFix-type tactics made up nearly half of the AI-themed campaigns it studied. Fake command-line interface (CLI) installers or InstallFix attacks represented 27% of the analyses, while traditional ClickFix attacks that began with fake download pages accounted for 17%. Meanwhile, attack chains that began with abused AI chats or malicious artifacts represented 25%.

"Fake AI and ClickFix are closely connected," the Any.Run spokesperson says, highlighting that 45% of the analyses involved the threat actor asking a victim to copy and paste a command into their interface. "This shows how widely attackers are already combining AI-themed lures with ClickFix techniques."

Related:'BigDiskBuster' Leaves Microsoft Defender Running While Blocking Updates

The lures typically offer fake CLI installers for various AI tools on GitHub pages or copied documentation hosted on trusted platforms such as Cloudflare Pages, GitLab Pages, Google Sites, GitHub, or even the AI platforms themselves, primarily targeting developers. Meanwhile, fake ads and SEO poisoned search results are usually aimed at marketing personnel.

"We expect fake AI lures to become even more common as new AI tools continue to launch and public interest remains high," the research team says. "People often search for installation instructions without knowing which sources to trust, and attackers take advantage of this."

AI-themed InstallFix and ClickFix variants are designed to compromise developer workstations to obtain a target organization's source code, SSH keys, CI/CD tokens, and cloud and AI API keys. "This approach is particularly effective against developers, since installing legitimate AI coding tools often involves running terminal commands," the spokesperson says. "That makes malicious instructions easier to disguise as normal installation steps."

And while marketing professionals may be less attractive targets for threat actors, Any.Run warned that those attacks could compromise credentials for high-value business accounts.

Risky Artifacts & AI Chats

In addition to increasingly prevalent InstallFix and ClickFick attacks, other types of AI-themed threats are also gaining steam. For example, a technique known as "LLMshare" has proven quite effective, according to Push Security.

LLMShare involves threat actors creating content on AI platforms in shared chats that often appear to offer installation guidance and service updates that contain malware, using malvertising and SEO poisoning to drive traffic to the malicious chats. Shared artifacts follow a similar track, as the attackers publish the malicious content directly to the AI platforms.

"The recent variants using shared chats, artifacts, and most recently custom GPTs are particularly nasty," Dan Green, researcher at Push Security, tells Dark Reading. These are legitimate AI sites (it's the real Claude, ChatGPT, etc. domain), and so people don't expect to be served a malicious link there.

Green adds that, like InstallFix, LLMshare has proven to be very effective, because it takes advantage of "very normal interactions and behaviors online" in today's era of rapid AI adoption. In fact, AI-themed InstallFix attacks make up 5% to 10% of Push Security's monthly detections, and the number is growing every month.

"Today, everyone is encouraged to use AI tools, and many are legitimately installed via the command line," Green says. "You have regular users working more like developers, making it easy for attackers to manipulate them."

Any.Run researchers emphasized that because many of these attacks are using legitimate domains and are sometimes hosted directly on the very AI platforms they're trying to use, detection can be challenging. But there are ways to mitigate the threat, starting with employee behavior.

"Every pattern in this research starts with an employee looking for an AI tool on their own," the report stated. "Publish a short list of approved AI tools with their official sources (vendor site, winget, Homebrew, or the vendor's package) and install them through MDM or the software portal."

Any.Run researchers also recommended that security teams restrict standard users' ability to paste and run commands, while also training employees to always verify install commands against a vendor's official documentation rather than relying on third-party links, ads, shared chats, or other sources.

Networking problems after the October 2026 Windows update? NTLM might be to blame

news The Register · 2026-10-16 · ↗ original

The October 2026 Windows security update may break networking for some customers who are still clinging to long-deprecated NTLMv1 security. A seemingly minor change in the update could have major implications for administrators and enterprises that haven't fully moved away from the legacy technology. Before the October 2026 update, Windows permitted NTLMv1-derived credentials for Single Sign-On and generated warning events. After the update, requests to use NTLMv1-derived credentials are blocked. It comes down to the BlockNtlmSSO registry value. If it hasn't been set, Windows will now use Enforce mode (1) instead of Audit mode (0), thus blocking requests and potentially impacting Wi-Fi, Ethernet, and VPN authentication, and therefore connections. The update does not set the value of BlockNtlmSSO, and administrators can set it to 0 to temporarily allow NTLMv1-derived Single Sign-On credentials. However, Microsoft noted, "Using Audit mode reduces the protection provided by Enforce mode and should only be considered as a scoped, temporary security exception." To be clear, this is not a bug and is by design. The addition of NTLM to the deprecation list occurred in 2024, and Microsoft added audit logs for NTLMv1 usage in late August 2025. The Windows giant has made no secret of its desire to ditch the legacy technology, stating in 2023, "Our end goal is eliminating the need to use NTLM at all." The problem is NTLM's longevity. It appeared in 1993 with Windows NT 3.1, and removing it from enterprise environments has proven tricky, even though it is somewhat insecure by modern standards. Microsoft removed it from Windows 11 24H2 and Windows Server 2025, but some remnants can still be found, notably when using MS-CHAPv2-based connections, including PEAP-MSCHAPv2, and EAP-MSCHAPv2, in a domain-joined environment. Hence the introduction of the audit mode in 2025, to help administrators spot where the technology was still being used. It is now 2026, and Microsoft has taken the next step. If Credential Guard is not enabled and BlockNtlmSSO is not set to Audit mode (0), the use of NTLMv1-derived credentials will be blocked as Microsoft works "to finalize the disablement of NTLMv1." There is no indication of how long the BlockNtlmSSO workaround (setting the value to Audit mode) will work - most likely until the next major Windows release. In September, Microsoft said, "In-market versions of Windows client and Windows Server will continue to support NTLM." However, it also stated, "Our long-term objective is a Windows platform that doesn't need NTLM at all." As such, if the message wasn't already clear, the move to enforce it by default makes it impossible to miss. The technology still exists in the operating system, but it is on its way out and will be removed in a future Windows release. Problems with networking after the October 2026 Windows security update could therefore signal that migration plans are not as far along, or as complete, as administrators might have thought. ®

In Other News: ICS-Sniper Attack, Hacking XWorm Malware Operators, $250k Chrome Exploit

news SecurityWeek · 2026-10-16 · ↗ original

SecurityWeek’s weekly cybersecurity news roundup offers a concise overview of important developments that may not receive full standalone coverage yet remain relevant to the broader threat landscape.

This curated summary highlights key stories across vulnerability disclosures, emerging attack methods, policy updates, industry reports, and other noteworthy events to help readers stay well-informed about the evolving cybersecurity environment.

Here are this week’s highlights: 

ICS-Sniper attack picks off critical OT traffic

University of British Columbia researchers have detailed ICS-Sniper, a proof-of-concept attack aimed at industrial facilities that rely on cloud-hosted SCADA systems. An attacker who controls a router on the network path could study the size, direction and timing of VPN-encrypted packets to predict when critical commands or data will be exchanged, then drop payload-carrying packets during those windows. In tests on emulated versions of the SWaT water treatment testbed, the attack delayed the start of clean water pumping by about 15 minutes and, in a separate test, kept a valve open more than nine minutes longer than intended.

Intel pulls SGX from Xeon roadmap after Diamond Rapids

Intel says Diamond Rapids, its next-generation Xeon platform, will be the last to include SGX, as it focuses its confidential computing roadmap on TDX. The company says the industry has moved toward VM isolation technologies like TDX because they’re easier to deploy and scale. Platforms with SGX will keep receiving support and security updates into the early 2030s, giving customers several years to migrate.

XWorm operators’ panels open to takeover 

Mootoo, an independent researcher based in Oman, has published a PoC exploit for an unauthenticated RCE flaw in the XWorm RAT’s C2 panel (versions up to 7.4). The researcher found it on October 4 while reverse-engineering an XWorm sample used in an attempt to compromise them. An attacker who has the panel’s address, port and communication key (all of which can be pulled from an XWorm client’s configuration) can pose as an infected machine, overwrite a DLL through path traversal, and get code running on the C2 host without any action from the operator. Mootoo told SecurityWeek they used the flaw to compromise infrastructure tied to the person behind the attack, and that it appears to be exploited on a limited scale.

Bank of America brings in patch army after Mythos

Bank of America CEO Brian Moynihan told CNBC that the bank brought in 1,000 outside contractors in the second quarter to help its 3,000-strong internal team fix flaws in proprietary and vendor software exposed by frontier AI models such as Anthropic’s Mythos. The contractors are still working there. Moynihan said the remediation effort, together with anti-money laundering compliance work, added a ‘couple hundred million plus’ to third-quarter costs, but he expects remediation costs to decline over time.

Anthropic catalogs Claude’s rule-bending on real websites

Anthropic has disclosed cases where Claude models took unintended actions on live websites during evaluations and internal use. In one case, a model exploited an injection flaw to run commands on a university server. Others involved submitting an invented tip through a Philadelphia Police Department form, and using exposed access tokens to reach fee-gated data. The company describes the impact as minimal, but it has now cut live internet access for all internal evaluations until it confirms its new detection tooling (which blocked every documented case in testing) works reliably.

West African scam centers targeted by tech giants and law enforcement

Meta, Coinbase, Google, Microsoft, OpenAI and ten other tech firms joined law enforcement from ten countries in a UK NCA-hosted operation against scam networks in Nigeria, Ghana and elsewhere in West Africa. Meta removed more than 3.7 million Facebook and Instagram accounts, pages and groups. Authorities arrested 28 people and rescued 117 trafficking victims who had been held in a scam compound, and the FBI said at least $11 million in potentially freezable funds was identified.

Burger King Japan app breach exposes 11 million member records

BK Japan, which runs Burger King’s official app in Japan, says hackers accessed the system holding the app’s member data between October 2 and October 7, exposing roughly 11 million member records. Exposed details include names, email addresses, phone numbers, dates of birth, gender and prefecture. The company says it doesn’t store card numbers and has so far found no sign that login passwords were taken.

AI-aided Chrome exploit for Windows takeover earns $250,000

XBOW has detailed a Chrome full-chain exploit, built by its researchers with help from OpenAI’s GPT-5.6 Sol, that let a malicious website take over a Windows machine. The final chain combines three bugs, all now fixed by Google. It was assembled in six days in August, after Google said it already knew about one of the flaws in the team’s first attempt. Google awarded XBOW a $250,000 bounty, while the compute required to develop the exploit cost $40,000.

KGB RAT pairs data theft with jump scares

Group-IB has analyzed KGB RAT, a Windows trojan sold on underground forums as a “fully undetectable” remote administration tool, with subscriptions ranging from $150 per month to $800 per year. Built on NjRAT foundations, it offers credential theft, keylogging, hidden VNC, ransomware and a crypto clipper. It also includes harassment features such as screamers, jump scares and forced blue screens. The developers push daily crypter updates to evade Windows Defender, and the samples Group-IB examined point to multiple operators using a shared builder.

Langflow flaw under attack weeks before CVE went public

Previdian says its honeypot sensors have recorded exploitation attempts targeting CVE-2026-105740, a critical Langflow vulnerability. The flaw lets any authenticated user run code on the server by adding an MCP server set to use the Stdio transport, because the supplied command is passed to bash without validation or sandboxing. The bug is fixed in version 1.9.0. Previdian first saw attempts on September 19, more than two weeks before the CVE was published on October 5, and has since logged over 1,800 attempts from 28 IP addresses in 16 countries.

Baltimore suburb confirms August data breach after ransomware claims

news The Record · 2026-10-16 · ↗ original

Officials in Anne Arundel County, Maryland, confirmed that hackers stole files from government systems during an incident in August. 

A county spokesperson told Recorded Future News that they discovered “irregular activity” on August 28 and began an investigation on a “limited subset of systems within the county computer network.”

“Through the course of the county’s response and investigation, it was determined that an unauthorized actor gained access to a limited number of systems and copied certain files from those systems,” the spokesperson said. 

The spokesperson did not respond to questions about what data was involved but said investigators are currently reviewing the files to determine whether any stolen information related to residents of the county. 

The Baltimore suburb is home to more than 600,000 residents and the state’s capital of Annapolis. Washington, D.C. is nearby, as well. Dozens of federal agencies have offices or headquarters in the county, including the Defense Department, the Internal Revenue Service, the Environmental Protection Agency, the Social Security Administration, the Department of Agriculture, the U.S. Coast Guard and more. 

County officials said they notified federal law enforcement about the data breach as well as other government agencies. 

The attack was claimed by the Rhysida ransomware gang, which threatened to leak 2.6 terabytes worth of documents stolen from the county if a $2 million ransom was not paid. 

The group recently attempted to extort the government of Berlin after stealing troves of emails and contracts from government systems. 

Rhysida has repeatedly targeted governments across the globe since emerging several years ago. Its victims include Kuwait’s Finance Ministry, the city of Seattle and the city of Columbus, Ohio and even the transportation department of Maryland.

Anne Arundel County dealt with a ransomware attack by a different group last year that forced the government to shut off multiple systems.

In a stroke of bad luck, the county released a new statement about last year’s attack on Thursday evening, telling residents that it planned to send out breach notification letters about leaked data in that incident on October 19. 

A spokesperson for the county told Recorded Future News that the August 28 attack is a “separate incident.”

The Anne Arundel County spokesperson added that recent reports “indicate that there has been a surge in these kinds of calculated cybercrimes specifically targeting state and local governments.” 

Cities and counties in New Mexico, Utah, Texas, Nebraska, Missouri and Arizona have all dealt with service outages over the last two weeks due to cyberattacks.

Investigating Ephemeral Supply Chain Tampering

threat-intel Google Threat Intelligence · 2026-10-15 · ↗ original

  1. Update Configuration (down_html.ini): The software periodically sends an HTTPS request to https://www2.aomeisoftware.com/download/abpopup/down_html.ini. This file contains the version number, the MD5 hash of the expected update package, and the URL where the client should download upgrade-now.zip.

  2. Notification Configuration (Notifycfg.ini): The software contacts https://account.aomeitech.com/Notifycfg.ini. This file instructs the local notification process (ABNotify.exe) what messages to display and specifies commands or programs located in the software’s local directory to execute.

Under normal conditions, these files direct the client to download official files hosted on AOMEI’s own domain (www2.aomeisoftware.com).

Campaign Overview

Rather than maintaining a persistent, static modification on the vendor’s distribution servers, GTIG and METAL’s telemetry indicates UNC7017 conducted repeated, short-burst configuration tampering. We confirmed several tampering windows in 2026, alongside related malware samples observed in the wild starting in late April. However, given the short duration of these windows, it is probable that additional tampering occurred throughout the campaign that remained outside our visibility. Systems checking for updates during an active window received malicious instructions, while systems checking before or after received clean, authentic files. 

During the brief tampering windows, the threat actor modified the update settings file on the update server to redirect the software to download a malicious ZIP package from attacker-controlled servers instead of legitimate updates. The threat actor also altered the notification settings file on the update server to abuse the software’s automatic notification service, forcing the system to immediately execute the downloaded malware locally. If a user’s application checked for updates while the threat actor’s modifications were active, then the application would download the trojanized update and execute malware. 

In cases where altered configuration files were active, the threat actor directed clients to download a weaponized ZIP archive containing CROSSROAD, an initial downloader responsible for environment validation and staging secondary components. CROSSROAD subsequently established scheduled task persistence to deploy SHINYROAD, a modular backdoor framework delivered via trojanized administration utilities to facilitate covert command and control.

Short Burst Supply Chain Tampering

A defining characteristic of UNC7017's operational security is its reliance on ephemeral, time-compressed server modifications. Across all directly observed waves, the adversary avoided leaving malicious configurations resident on AOMEI's update servers:

  • May 28: 10-minute exposure window (05:40 – 05:50 UTC)

  • July 16: 6-minute exposure window (08:33 – 08:39 UTC)

  • July 20: 5-minute exposure window (10:35 – 10:40 UTC)

At the conclusion of each window, UNC7017 reverted both down_html.ini and Notifycfg.ini to their legitimate contents. This hinders post-incident vendor audits, minimizes the window for network defenders to capture live malicious server responses, and restricts compromise to clients polling for updates during those exact minutes.

Two Config Files, Two Release Tracks, and One Very Bad Commit

red-team TrustedSec · 2026-10-15 · ↗ original

Part 3 of 3. Part 1 is the reference for every attack and feature added to hate_crack since 2.0. Part 2 is the deep dive into HashcatRosetta. This post is the plumbing: where configuration lives now and why it moved, how releases get cut, and the afternoon I pushed my private notes to a public repository.

Story Time

On July 30, a prek pre-push hook corrupted my git index.

The mechanism is a stash and restore cycle. The hook stashes your working tree so the checks run against what you're actually pushing, then restores it afterward. When that cycle went wrong, the index it handed back was not the index I'd built. The commit that came out of it deleted 85,280 lines across roughly 165 files and staged a pile of gitignored, local-only paths: CLAUDE.md, .claude/, docs/plans/, docs/superpowers/.

Those paths were not gitignored by accident. I purged them from this repository's history on July 25, five days earlier, specifically because trustedsec/hate_crack is public and those files are my working notes.

It reached the public remote before I force-pushed it away.

The part that stings is how little was standing in the way. detect-private-key was the only secret-scanning gate in the whole project, and it does not look at any of this. CI had nothing at all. The publication boundary existed in a .gitignore file and in my head, and git add -f walks straight past the first one.

So, the boundary is enforced at commit time now, by two scripts in .github/scripts/.

check-publication-boundary.sh refuses any commit that adds or modifies one of those paths. The important detail is that it reads the staged changeset out of the index with git diff --cached --name-only --diff-filter=ACMRT rather than consulting .gitignore, because forcing past .gitignore is precisely the failure mode it exists to catch. Deletions stay allowed, so an accidentally tracked boundary file can still be removed. There is no override, and that's deliberate.

check-mass-deletion.sh aborts any commit deleting more than 50 tracked files. No commit in the last 400 in this repository's history deleted more than one, so 50 sits two orders of magnitude above real work while still catching a whole-tree wipe. When you genuinely mean it, HATE_CRACK_ALLOW_MASS_DELETE=1 is the escape hatch, and it's the right one to reach for instead of --no-verify, which would also skip the boundary check.

Both are pre-commit hooks, not pre-push, and that placement is the whole lesson. By pre-push time, the bad commit already exists in your local history, and the pre-push stash is itself the thing that corrupts the index. A guard that runs after the damage is a report, not a guard.

The failure messages carry the actual recovery, because the symptom is fatal: this operation must be run in a work tree and that tells you nothing about what to do. git config core.bare false, then git reset HEAD, then git status --short and expect it empty. Nothing on disk is ever lost in this failure. It just looks like everything is.

tests/test_commit_guards.py runs both scripts as real hooks against throwaway repositories and asserts on whether git commit actually succeeded, rather than grepping prek.toml for hook IDs. Neuter either script to exit 0 and its tests fail. That distinction is not academic as it already bit this project once, where deleted code got reinstated with the whole suite still green.

The Purge that Didn't Purge

Here's the part I got wrong, and I only found it while auditing for something else.

A .gitignore plus a history rewrite does not unpublish anything on a repository that takes pull requests. GitHub's refs/pull/N/head is server-side and immutable. The July 25 filter-repo rewrote every branch and left every PR head exactly where it was, so those files stayed fetchable from PRs #78 through #137 the entire time I believed they were gone. Nothing bad came of it, and the only reason nothing bad came of it is that the content turned out to be clean.

The lesson is not "purge faster." It's that the gate has to be never commit it, because after that, you are negotiating with a service that keeps its own copies. Which is, incidentally, the same conclusion the pre-commit hooks above arrived at by a different route.

Then, I went the other way with it. As of 2.33.0, CLAUDE.md and .claude/ are published on purpose. Keeping them out meant this project's branching, release, tagging, and config policies were documented nowhere a contributor could read them. You could see that main only ever receives work through a batch integration merge, but not why, nor that history has to stay linear, nor that a Closes #NNN in a work-branch commit closes exactly nothing.

The boundary narrowed rather than disappeared. Still refused: .claude/plans/, .claude/specs/, docs/plans/, docs/superpowers/, and .claude/settings.local.json. Plans and specs are per-task scratch written in the future tense, stale the moment the work lands, and a reader can't tell a shipped design from an abandoned one. Four of them from April were dropped rather than published. One announced itself as superseded by another in the same batch, and between them they referenced two test files that no longer exist.

All four enforcement layers narrowed together, and the guard tests now assert the narrowing in both directions, so a revert that re-forbids CLAUDE.md fails the suite instead of quietly un-publishing it.

Publishing .claude/ bought a new problem, though, and tests/test_agent_instruction_integrity.py exists for it. A pull request can now propose changes to files a maintainer's coding agent reads as instructions and, for hooks, executes as code, without touching hate_crack/ at all. Every hook command, hook script, subagent definition, skill, and shell script under .claude/ is pinned to a literal approved set. A permissions key in the shared settings.json is refused outright, since that proposes auto-approval rules for everyone who trusts the workspace rather than just its author. Any network verb in a .claude/ script is refused too, because a hook that reaches the network can exfiltrate whatever the session has read.

The marker scan for crude instruction-override phrasing is a lint, not a boundary, and the module docstring says so, because no parser settles the intent of natural language. What the file actually buys is that a change to that surface can't be silent. All six vectors got mutation-tested, and each one fails the suite.

Your Config is Now Two Files

The other big change since 2.17 is that configuration split in two, and this one is breaking.

config.json keeps operational settings: paths, wordlists, and candidate caps, which attacks pass -O. A new .env holds third-party integration settings which, in practice, means every credential: Hashview, Hashmob, Pushover, and the Ollama connection details.

The rule that makes it work is that every key has exactly one home. A key is read from its home file and nowhere else. Put hashview_api_key in config.json and it is ignored, with a warning naming the file it belongs in:

Config key 'hashview_api_key' in /path/to/config.json is ignored: it belongs
in the .env file, as HASHVIEW_API_KEY. Remove it from /path/to/config.json.

Precedence has three layers and no cross-file fallback:

  1. The real process environment
  2. That key's own home file, and only that file
  3. The schema default

The process environment is the one exception to the one-home rule, because it isn't a home. It's an ephemeral override, which is what keeps HASHVIEW_URL=... hate_crack working for a single run against a dev stack without touching persisted config.

Both files resolve independently through the same search order: repo root, then the installed package directory, then ~/.hate_crack. They're allowed to live in different directories.

One empty-string subtlety is worth knowing, because it will look like a bug otherwise. In .env, an empty value is a deliberate statement: PIPAL_PATH= means "no pipal" and does not fall through to the default. In the real environment, an empty value is treated as unset and does fall through. This matches how the old code read, os.environ, and keeps a stray export from meaning something different than a written line.

What Happens to Your Existing Config

Nothing gets deleted behind your back. On first run after the upgrade, if you have a config.json with integration keys in it and no .env yet, a one-shot migration runs. Then, it copies those keys into a fresh .env created 0600, backs the original up to config.json.pre-split.bak, and rewrites config.json without the keys it copied. Everything else in that file survives verbatim, in its original key order, so the diff is reviewable.

A value with the wrong type doesn't get copied. The .env gets the schema default instead and the migration says so, rather than carrying a broken value into the new file quietly.

If the rewrite of config.json fails, the migration still counts as done and tells you to finish by hand:

Could not rewrite /path/to/config.json to drop the copied keys; they are now
read from .env only, so delete them by hand to stop the warnings.

Two lines print at the top of every run naming exactly which files are in effect:

[*] config.json: /path/to/config.json
[*] .env:        /path/to/.env (created this run, from built-in defaults)

That output exists because of two facts that are otherwise invisible. The search order prefers a repo checkout over ~/.hate_crack, so a stray .env in any checkout silently outranks the real one. A .env in your current working directory is never read at all, which is deliberate. Engagement directories are full of files nobody intended as config.

A dangling .env or config.json symlink is now fatal instead of being ignored. os.path.isfile() reports a broken symlink as absent, so before that fix a broken symlink meant silently falling back to schema defaults: wrong wordlists, wrong potfile, and no indication anything was off.

The Local Model that Wasn't Local

Ollama will proxy a cloud-hosted model for you. Tag a model gpt-oss:120b-cloud or deepseek-v3.1:671b-cloud and requests to it go to ollama.com, through the same localhost endpoint a local model uses. Nothing about the request shape tells you the prompt is leaving the host.

The prompts hate_crack's LLM attack sends carry recovered plaintexts, corpus statistics, and the client's name, industry, and location.

The model name was the only thing I checked at first, because it's the only thing you can look at before the data is already gone. Set OLLAMA_NO_CLOUD=1 in .env and a -cloud-tagged model is refused before a client is constructed or a request assembled:

'gpt-oss:120b-cloud' is an Ollama cloud model and OLLAMA_NO_CLOUD is set.
Prompts carry client corpus and target details, so this request was not sent.
Pick a locally-hosted model, or unset OLLAMA_NO_CLOUD in your .env.

It defaults to off, because anyone deliberately using a cloud model shouldn't have their tool argue with them. Turn it on if your engagement paperwork means what it says. The check lives at the three hate_crack.llm entry points rather than at their call sites, and its no_cloud parameter is keyword-only with no default. Therefore, a new call site has to state a policy instead of inheriting a permissive one by omission.

Checking the name was never good enough, though, and once vLLM and OpenAI-compatible backends landed it stopped being defensible at all. A model tag tells you nothing about where the request goes when the endpoint itself is the thing pointed offsite. So OLLAMA_NO_CLOUD guards the destination now, through llm.is_offsite_url(), for all three backends.

The rules it applies are the ones you'd write yourself, plus two you might not. localhost, loopback, private, and link-local are local, as is anything ending in .local, .internal, .lan, or .localdomain. A hostname resolving to a mix of private and global addresses counts as offsite, because one global address is enough for the prompt to leave. A hostname that fails to resolve is treated as offsite, which is the fail-closed call. Somebody who set OLLAMA_NO_CLOUD asked for "nothing leaves this host," and refusing a destination the function can't verify honors that better than waving it through.

The two you might not write are as follows. One is CGNAT (100.64.0.0/10) because it is treated as local, because Tailscale hands out tailnet addresses from that range, and a GPU box reached over Tailscale is an ordinary remote-but-private setup rather than cloud egress. The other is 6to4 (2002::/16) because it is always offsite, since it encodes a global IPv4 address by definition no matter what it looks like.

While I was in there, I found that OLLAMA_HOST had never worked from .env. It was read straight off os.environ, but the loader parses .env with python-dotenv's dotenv_values(), which returns a mapping and deliberately does not export into the process environment. So, an OLLAMA_HOST was written into .env, which is where every other Ollama setting lives and where .env.example implies it belongs. This was reported as an unrecognized key, ignored, and the run talked to localhost:11434 while I believed it was talking to my GPU box. It's a real schema key now. A genuinely exported OLLAMA_HOST still overrides it for a single run.

That bug is exactly what the missing read-site test would have caught, which is why that test exists now.

Eight Flags that Remember

Eight command-line preferences used to have to be restated every single run. They're schema-backed defaults now, and the flag is a per-run override: --debug, --rank, --nightly, --restore-potfile, --potfile-path, --no-optimized-kernel, --rule-debug-mode, and --coverage.

The last two arrived with the features behind them. rule_debug_mode_enabled (default true) decides whether rule attacks write the hashcat debug log that the Rosetta Attack later reads. coverage_enabled (default true) decides whether hate_crack records what it already ran against a hash file. Both default on, and both are things you'd want off in exactly one situation: A run where you don't want anything about it written to disk.

Precedence is the flag, then the environment, then the file, then the default. The Booleans moved off store_true onto argparse.BooleanOptionalAction with default=None, because store_true cannot express "explicitly off" because absent and deliberately-false both read as False. None now means defer to config, and each has a real negative form, so --no-restore-potfile genuinely overrides a config that enables it.

--nightly is the one you'll notice, since the update channel is a persistent setting now (update_channel, default main, and it validates against a closed set of main and nightly-dev).

Two of these got renamed within a single release cycle, and the reason is worth stealing. DEBUG and UPDATE_CHANNEL became HATE_CRACK_DEBUG and HATE_CRACK_UPDATE_CHANNEL, because an ambient export DEBUG=1 in somebody's shell profile would otherwise silently enable debug logging, and debug logging writes cracked plaintexts to disk. Namespace your environment variables. A generic name is a loaded gun in a shared shell.

Can You Trust the Tags?

If you contribute, or you just want to know whether a release is worth pulling:

CI runs ruff, ty, and pytest on Python 3.13 for every pull request and every push to main or nightly-dev, plus bandit against a baseline so only new findings fail, and pip-audit for known CVEs. The nightly-dev trigger is not decoration. Without it, pushes to the branch that cuts every release candidate would run no CI at all, and the nightly tag workflow gates on it. Tagging is gated on it passing, so a release can only be cut from a commit CI validated, regardless of whether the author had local hooks installed.

The suite is 3,246 tests across 136 files. A pile of it is opt-in behind environment variables, because it wants real binaries, real API credentials, or Docker: HATE_CRACK_RUN_E2E=1 for the non-interactive subcommands end to end, HASHVIEW_TEST_LOCAL=1 with HASHVIEW_REPO=<path> to spin up a real Hashview docker stack and tear it down after, HASHMOB_TEST_REAL=1 and friends for live API calls, HATE_CRACK_RUN_LIMA_TESTS=1 for a macOS VM install. CI runs none of those, and it doesn't install hashcat either, so a few of the best tests in the project are local-only by construction.

The Part Where Auto-Tagging Got Away from Me

hate_crack is the first project where I wired up automatic version bumping. I should be straight about how that went, because the tidy description above reads better than living with it did.

The original scheme derived the bump from Conventional Commit subjects. fix: cuts a patch, feat: cuts a minor, CI gates the tag, nobody has to remember anything. The logic is sound. What I hadn't thought through is that it does exactly what I specified, every single time, with no sense of proportion whatsoever.

On July 28, I sat down and worked through a batch of PCFG and config-loading bugs. Every one was real and every fix honestly earned a patch bump under the rules I'd written. Eight releases came out of that afternoon, v2.14.4 through v2.15.1, and the 2.14 line went all the way to .9.

The dates tell the story. Weeks of nothing, then six tags on the 24, three on the 25, eight on the 28. That isn't a release cadence, it's a commit log with version numbers stapled to it. Anyone watching the repo got eight notifications for what was, from outside, one guy cleaning up after himself. Worse, ‘Which version should I be running?’ stopped having a useful answer, because the answer was always, ‘The newest one, there's a new one every ninety minutes.’ If you go count, it got worse before it got better. The 29 has 46 tags on it, but 41 of those are release candidates, because the 29 is the day candidates started existing at all. That they were candidates in the wrong format is the next section.

I'd been asking the tags to do two different jobs. One is marking a commit CI validated, so it's addressable and someone can bisect to it. The other is announcing that something is worth pulling. Those look identical right up until you cut eight in a day, at which point the second job is broken and you've trained everyone to ignore the first.

Now There are Two Tracks

Development lands on nightly-dev and gets tagged there. It merges to main cut releases. A plain git pull on main gets you releases, and --nightly or the branch gets you what's landed since.

That scheme has since been rewritten twice, and if you read the tags, you're looking at the third version of it.

Nightly tags are release candidates aimed one version forward. The tags now look like v2.33.1rc1, v2.33.1rc2, and so on, then v2.33.1 when the batch merges down. They're real PEP 440 pre-releases, so they sort where you'd want:

2.33.0  <  2.33.1rc1  <  2.33.1rc12  <  2.33.1  <  2.34.0rc1  <  2.34.0

Getting that ordering right took two failed attempts, and both failures are ones you could reproduce. The first scheme tagged v2.19.0-rc.N, aiming candidates at the version the branch was currently on rather than the one it was heading for, so every candidate sorted below the release it was a candidate for. The second scheme fixed that by dropping the pre-release marker entirely and cutting ordinary final versions, which fixed the sorting by making every nightly outrank the last real release. The answer wasn't to abandon pre-releases. It was to aim them one version forward.

The target can move mid-cycle. The first feat to land shifts the batch from X.Y.(Z+1) to X.(Y+1).0, and candidate numbering restarts. That's intended, because the number is supposed to name what the batch would ship as today, not what it looked like when it opened.

The bump comes from what's actually in the batch, and the policy lives in Python.nightly-dev cuts candidates, main promotes the same target to its final. Any feat since the last release means the batch is heading for a minor, and a batch of nothing but fixes, docs, and chores is heading for a patch. Roughly 70 lines of cut -d. and $((minor + 1)) duplicated across two workflows went in the bin, replaced by tools/next_version.py, which both workflows call. Everything above the git boundary in it is pure and unit-tested. Release policy expressed in YAML is policy that cannot be tested, and it was wrong twice.

Which means a docs-only merge to main still cuts a release, and I'm at peace with that. A merge to main is an explicit release event, and I'd rather have a boring version number than a special case.

The major component is never bumped automatically. A ! subject or a BREAKING CHANGE: footer counts as a feature and cuts a minor, because an automatic major is an irreversible published mistake waiting on one mistyped subject line. A major stays a human tagging and pushing it by hand.

One non-obvious detail in there that took a bug to find. The baseline is the highest final tag in the whole repository, deliberately not restricted to tags reachable from HEAD. main's release tag can sit on a commit that the nightly-dev tip doesn't contain, and a reachability-restricted lookup then computes the next nightly from a stale baseline and hands out a version below the release that already shipped.

Two traps in here are worth stealing if you build something similar. A workflow_run trigger checks out the tip of the default branch by default, not the commit whose CI run just finished, so a naive version of this validates one commit and tags a different one. Pin ref to github.event.workflow_run.head_sha. The nightly workflow has to exist as a byte-identical copy on both branches, because GitHub only dispatches workflow_run for workflows present on the default branch. I verified that one the hard way. The CI passed on nightly-dev and the workflow simply did not run.

There's also a guaranteed red window baked into the design. cz bump fails with [NO_VERSION_SPECIFIED] on any nightly-dev commit whose pyproject.toml lacks the [tool.commitizen] block, which is exactly the gap between a workflow change landing on main and the next merge down. The error says nothing about the cause. If you see it, merge main into nightly-dev.

Reconciling Tags Across Parallel Worktrees

Here's the part that took me longest to understand, and it only shows up if you work the way I do. I run several git worktrees at once, one per task, so a few changes are in flight in parallel rather than queued behind each other.

No version string is hardcoded anywhere in the source. pyproject.toml declares dynamic = ["version"] and hands the job to setuptools-scm, which derives it from git describe at build time. That's the right design and I'd do it again. It also means the version is not a property of your code. It's a property of your refs.

Those two facts collide in a specific way. Tags live in the shared common git directory, so every worktree sees the same tag set, but git describe answers from whichever tags are reachable from that worktree's HEAD. Two worktrees branched from different points on main, building at the same moment, legitimately derive different versions.

Then, add eight tags in an afternoon. A worktree I created before lunch derives its base version from a tag three releases have since superseded, and nothing in that worktree knows it. The fix is git fetch --tags, which is easy once you know and invisible until you don't. The sharp edge is the shared ref store cutting the other way. A fetch in one worktree changes the version every other worktree derives, without touching a single file in any of them. Watching a version number change between two builds of a byte-identical tree is a genuinely disorienting thing to debug the first time.

However, there's a wrinkle that makes it easier to miss. hate_crack/__init__.py reads the version out of installed package metadata and deliberately strips the suffixes for display, so 2.5.1.post1.dev0 prints as 2.5.1. That's the correct call for a user-facing banner, because nobody wants build metadata in their terminal. It also throws away exactly the part that distinguishes two builds from two different worktrees. Both announce the same clean version while containing different code.

None of that is a setuptools-scm bug, and splitting the tracks didn't fix it. It's what you sign up for when the version comes from git instead of a file. Refs need reconciling the same way code does. What I do about it is fetch tags before trusting any version a worktree reports, and never compare .dev distances across two branches, because those numbers only mean anything within a single line of history.

The Name on PyPI is a Trap

pip install hate-crack does not install hate_crack, and it never will.

The name is a placeholder I published to keep it from being squatted, because a package squatted under that name would land on hosts holding client hash material and API credentials. There's a real threat model there and it isn't hypothetical.

The implementation amused me enough to write down. packaging/pypi-placeholder/ holds a PEP 517 backend that delegates build_sdist to setuptools and raises from build_wheel, prepare_metadata_for_build_wheel, and both editable variants. Since pip reaches one of those on every install, everyone who tries gets the message:

hate_crack is not installable from PyPI. The name on the index is a
placeholder held to keep it from being squatted; there is no package behind
it. Install from source instead:
    git clone https://github.com/trustedsec/hate_crack
    cd hate_crack
    make install

It's version 0.0.0, classified Development Status :: 7 - Inactive, declares no scripts, and ships no modules but the backend itself. It deliberately does not set requires-python, because pinning that makes pip report "no matching distribution" on older interpreters, which reads like a version problem instead of "this package does not exist."

Publishing is manual workflow_dispatch only, over PyPI Trusted Publishing with no stored token, and a test globs every workflow in the repo to assert none of the others reference it. An upload guard checks the artifact before it goes: Exactly one sdist, the right filename, Version: 0.0.0 and the word "placeholder" in PKG-INFO, and no .py file in the archive other than the backend.

Tests That Could Not Fail

Two rounds of test work since 2.17 were really the same lesson twice, so they belong together.

Four Hashview tests were passing without doing anything. Each took a fixture that holds patch("requests.Session") open for the whole test body, then built its own client inside the test, so that client's session was a MagicMock and no request ever left the process. The worst of them, test_get_hashfiles_by_type_success, asserted isinstance(result, list) against a method whose own except Exception: return [] satisfies that assertion perfectly. Total failure and complete success were indistinguishable.

The fix was splitting each into a mocked test and a real one gated behind HASHVIEW_TEST_REAL, with credentials from the environment only, asserting the session is a genuine requests.Session. I deliberately did not keep the old "real if possible, otherwise mock" fallback, because a green dot never said which branch ran, and that is what hid this for as long as it did. The helper that read config.json to build a client got deleted with its last caller, since a plain pytest run could otherwise reach a developer's real Hashview instance.

The guard on the live helper then needed its own fix. It checked isinstance(session, requests.Session) first, but patch("requests.Session") replaces the class too, so at the exact moment the guard should fire, it instead raised TypeError: isinstance() arg 2 must be a type. It checks against Mock first now and says what's actually wrong.

The other round was the mask generator, and the same shape shows up. Every existing test compared _mask()'s output against a hand-written expected string, which only proves the function agrees with my own belief about what ?l and ?d and ?s mean. I made hashcat the judge instead. I hashed a short synthetic plaintext, handed hashcat the mask _mask() produced, and asserted hashcat to recover it. A negative control asserts a deliberately wrong mask does not crack, so a potfile hit or an output-format change can't make the positive cases pass vacuously, and --potfile-disable is passed for the same reason.

That oracle immediately found a real bug. Masks were character-oriented and hashcat's are byte-oriented, so ab²x is four characters and five UTF-8 bytes, and no four-position mask can describe it under any charset. Non-ASCII passwords produced masks that were wrong in both charset and length, and those masks went straight into an LLM prompt as if they were usable. Non-ASCII passwords are excluded from the mask statistics now, with the excluded count reported alongside the eligible one so a corpus that's 30% non-ASCII doesn't quietly understate every share.

One of those tests exists purely to pin a fact the fix rests on: it runs hashcat --stdout -a 3 ?a, counts the lines, and asserts 95. If ?a ever covers more than the printable ASCII set, the whole non-ASCII mask problem changes shape and somebody needs to revisit this.

There's a third one now, and it's the worst of the three because the damage escaped the test that caused it.

hate_crack/main.py sets its own _path_ so it can be treated as a package when loaded standalone. Harmless-looking, right? The side effect is that a string-target patch through it, mock.patch("hate_crack.main.llm.generate_candidates", ...), gets resolved with pkgutil.resolve_name, and resolve_name imports each dotted prefix as a real module instead of following the attribute main.py already bound. So, that patch imports hate_crack.main.llm as a second, independent execution of llm.py: a distinct module object, with distinct classes. Then the import machinery rebinds hate_crack.main's llm attribute to the duplicate.

Mock's teardown restores the patched attribute on the duplicate. It has no way to know the rebinding happened, so the duplicate stays bolted to hate_crack.main.llm for every test that runs after it. This was confirmed live before the fix: hate_crack.main.llm.CloudDestinationRefused is not hate_crack.llm.CloudDestinationRefused, which means an except llm.CloudDestinationRefused somewhere else in main.py silently stops catching. One test's setup quietly breaks exception identity for the rest of the session, and nothing fails at the point of damage.

If you take one thing from this section, make it the differential shape. Both fixes replaced "assert the code agrees with what I wrote down" with "assert the code agrees with something that isn't me." That's the same instinct that runs through Part 2, where the only thing that ever settled an argument about hashcat rule semantics was hashcat.

Where to Start

If you're upgrading and you only do five things:

•Run it once and read the two config-source lines it prints. That tells you which files are actually in effect, which is not always the ones you think.

• Move your credentials to .env, or let the migration do it and then read the .pre-split.bak diff. The warnings will nag you every run until you do.

• Diff your config.json against config.json.example. Three dead keys came out and defaults moved, including the context window (now OLLAMA_NUM_CTX in .env) from 2048 to 8192, and hcatPotfilePath to auto.

• Set OLLAMA_NO_CLOUD=1 if you touch the LLM attack on client data. It costs you nothing unless you meant to send it offsite, and it checks the destination now, not just the model name.

• Set update_channel once instead of typing --nightly forever.

That's the pair of posts this one hangs off. Part 1 is the attacks. Part 2 is the rule engine.  This half is the stuff nobody reads until it's already wrong.

And if you've got a pre-push hook that stashes your working tree: your guard rails run after the commit exists. Mine did too, right up until the afternoon they didn't.
