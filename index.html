GitLab warns of new max severity code execution vulnerability

news BleepingComputer · 2026-10-22 · ↗ original

GitLab has released security patches for a maximum-severity Regular Expression Compiler flaw that can let remote attackers run arbitrary code on vulnerable servers.

This security issue is tracked as CVE-2026-110264 and was reported by a security researcher using the 'joaxcar' handle through GitLab's HackerOne bug bounty program.

CVE-2026-110264 stems from an integer overflow weakness in GitLab's Regular Expression Compiler, a background engine that parses and validates regular expressions in configuration files.

GitLab has fixed the vulnerability in GitLab Community Edition (CE) and Enterprise Edition (EE) versions 19.5.1, 19.4.3, 19.3.6, 19.2.9, 19.1.9, 19.0.10, and 18.11.13, and warned users to patch their instances immediately.

"GitLab has remediated an issue that, under certain conditions, could have allowed an unauthenticated user to execute arbitrary code on the GitLab server due to integer overflow when compiling a specially crafted regular expression," the company said.

"We strongly recommend that all installations running a version affected by the issues described below are upgraded to the latest version as soon as possible. [..] GitLab.com is already running the patched version. GitLab Dedicated tenants running 19.3.5-internal0 and 19.4.2-internal0 or later already include these fixes and do not need to take action."

Internet threat watchdog Shadowserver now tracks over 2,700 GitLab Community Edition instances exposed online, but it doesn't provide any information about how many of them are honeypots or have already been secured against attacks.

GitLab warned customers ten days ago about another critical remote code execution vulnerability (CVE-2026-97229) with a 10/10 CVSS base score in the CI/CD Regular Expression Compiler, reported by the same security researcher.

Last month, it fixed another maximum-severity GitLab CE/EE flaw (CVE-2026-85706) that lets unauthenticated attackers read sensitive data (e.g., credentials and other secrets) from vulnerable servers.

One day later, the U.S. Cybersecurity and Infrastructure Security Agency (CISA) added CVE-2026-85706 to its list of actively exploited flaws and ordered federal agencies to secure their systems within three days.

Since November 2021, CISA has flagged five GitLab flaws used in the wild, including one exploited in ransomware attacks.

GitLab's DevSecOps platform has over 30 million registered users worldwide and is used by over 50% of Fortune 100 companies, including Nvidia, T-Mobile, Lockheed Martin, Airbus, and Goldman Sachs.

Railway Says Intruder May Have Accessed Customer Secrets, Urges Credential Rotation

news The Hacker News · 2026-10-22 · ↗ original

Platform-as-a-Service (PaaS) provider Railway on Wednesday disclosed "anomalous activity" related to systems that store customer environment variables.

Upon further investigation, the company found that an unauthorized third party may have gained access to encrypted environment variables, and, in some cases, obtained the decrypted contents. The impact, it said, is limited to a "subset of users," although it did not disclose an exact number.

Environment variables refer to user-defined key-value pairs that are used to store sensitive data like API keys, database credentials, or feature flags. They are configured at the operating system or container environment level instead of hard-coding the values directly into a program's source code.

Railway said the incident is likely part of a series of attacks designed to target platform companies with the ultimate goal of compromising artificial intelligence (AI) inference providers. The company also said it has notified upstream providers to proactively revoke the keys so as to prevent their abuse.

Customers are being urged to take the following actions as a precautionary measure -

  • Rotate environment variables, including any API keys, stored in Railway, as well as private registry credentials.
  • Review logs for those services for unusual activity

According to security researcher Taylor Monahan (@tayvano_), the incident has also allowed the attackers (0xd9773325282874d18cb83f1fe50f14c39750b2ee) to drain cryptocurrency wallets whose private keys were stored on Railway. The first known cryptocurrency theft transaction is said to have occurred at 7:36 p.m., at least two hours before the incident was officially disclosed.

Railway has since rotated all Railway bucket credentials and invalidated Railway API tokens in response to the incident. It has also restored builds for Pro and Enterprise workspaces, allowing customers to apply new credentials added in Railway.

"Builds remain available for Pro and Enterprise workspaces," it said. "We are continuing to work on enabling builds for Hobby, then Free and Trial. Some builds are still failing more often than usual, and many deployments remain queued with longer than usual wait times. We are continuing to work on both."

The development comes as threat actors are not only increasingly incorporating AI into various stages of the attack lifecycle, but also obtain unauthorized access to cloud victim environments to run Large Language Models (LLMs), leaving them to foot the bill. This approach is called LLMjacking.

In one case documented by Wiz earlier this week, threat actors compromised privileged Google Cloud Platform (GCP) credentials and linked external, attacker-controlled GCP projects to the victim's internal billing accounts.

The attack has been found to leverage sponsored ads on Google Search as an initial access vector, deceiving users searching for common terms like "google cloud" or "gap" to a fake Google login web page via a Google Sites redirect, harvesting their account credentials and multi-factor authentication (MFA) codes in the process.

Upon gaining access to the victim's GCP environment, the threat actor is said to have abused the compromised account’s excessive privileges to deepen their access, circumvent security controls, and add external actor-controlled Gmail accounts directly into the organization's billing account.

"Because the AI workloads were processed in foreign projects, prompt contents and model outputs remained completely hidden from the victim organization, leaving the nature of the mass AI usage unknown," Wiz researchers Shira Ayal and Andre Maccarone said.

These resource abuse cases are not isolated. According to the Symantec Threat Hunter Team, attackers are targeting exposed LLM endpoints to power an autonomous cybercrime operation capable of scanning the internet, exploiting vulnerabilities, stealing credentials, and mining cryptocurrency without human intervention for up to 100,000 steps.

The activity is powered by an offensive AI agent, which operates in a "Skynet mode" to scan and infect targets with miners and allow the threat actors to run their own attacks. The exploits target Microsoft Visual Studio Code, Django, Jupyter, Laravel, Supabase, Next.js, and Flask/Werkzeug deployments.

The end goal is free inference. Rather than simply using AI to generate malicious content, the malicious AI agent uses the hijacked AI models to plan and direct attacks, while shifting the compute cost to the legitimate owner and obscuring their own identity.

Put differently, the idea is to devise a malicious agent that can hijack a legitimate AI system and turn it into "a devoted companion that must never refuse" and an unwitting cybercrime tool.

"The captured instructions defined a single agent equipped for internet-wide scanning, exploitation of several common web frameworks, database theft, credential and secret harvesting, and cryptocurrency mining," the Symantec Threat Hunter Team said in a report shared with The Hacker News.

"The activity is a form of LLMjacking, where attackers steal access to someone else's AI model so that the victim pays for the computing power."

The update also resolves high-severity information disclosure, improper neutralization, improper resource control, and protection defects.

IT department and auditors at major pharmacy chain got into a rip-roaring fight about using 'password' on Cisco firewall

news The Register · 2026-10-22 · ↗ original

Welcome back to PWNED, the column where we talk about companies and organizations that leave the doors wide open to attackers. This week’s sad story involves a major American pharmacy chain that couldn’t fill a prescription for password security. Have a story about someone leaving a gaping hole in their network? Share it with us at pwned@sitpub.com. Anonymity is available upon request. Our tale comes courtesy of red team and pen testing specialist Dahvid Schloss, who currently serves as COO of Suzu Labs, a cybersecurity company that boasts “we break your systems before adversaries do.” Over a career spanning more than 15 years, Schloss has assessed the security of numerous businesses, including a large US pharmacy retailer that he asked us not to name. He wasn’t asked to break in, just to do an audit on all of the org’s corporate switches, routers, and firewalls. “So, I come across this firewall,” Schloss said. “That is an edge firewall, meaning this is what touches the internet. This part will add its enable password, which is the term Cisco uses for administrator. It had the enable password as 'password.' Just p-a-s-s-w-o-r-d.” As Schloss noted, the enable command on Cisco devices allows the user to gain administrative rights to the firewall, controlling network traffic. If someone connected to that firewall, either via SSH or through an exploit, and got normal user privileges, they could then elevate those privileges to admin and do something like shut off all traffic from the intranet to the outside world. Schloss actually didn’t guess that the password was “password,” but instead was able to decrypt the file holding the passwords by breaking Cisco’s own protection, something he said is easy to do. “That enable password was stored as Cisco IOS type 7, which isn’t really a hash,” he said. “It’s more of a reversible encoding with a publicly known key. Even back then, it was best practice not to use it.” But even if the password were stored in a secure place, it would be very easy for a threat actor to guess. So he marked the password failure down as a “high find,” a bad type of vuln that needs to be fixed right away. When he brought the password to the company’s auditing department, they put him on a phone call with the auditing team, the entire IT team, his own manager, and others. On the packed call, the auditing team, who had commissioned Schloss’s work, was very concerned about the firewall password, but the IT team didn’t think it was a very serious problem. The two sides screamed at each other for more than an hour while Schloss and his colleagues sat there quietly, staring at their cameras. “The audit team is like ‘yeah, we gotta fix this.’ And the directors were really harping on ‘this needs to be done’ and the IT team starts firing back,” Schloss explained. “It’s like ‘Why? Who’s gonna? What does it matter? No, this isn’t a high-priority find. This is maybe a medium. Yeah, it’s bad, but it’s not that bad.’” The call dragged on so long that Schloss was unable to finish presenting his findings and recommendations. The conflict was so severe that the client continued to follow up and ask him to explain what he found again for the next three years – long after he had moved on to other projects. He later learned that the auditing department controlled the bonuses for the IT team and there was a stipulation that any “high finding” would eliminate those bonuses. So they weren’t just arguing about “password” - they were really talking about the compensation for an entire division. The lesson here is more than “don’t use the word ‘password’ as a password.” It's also about misaligned incentives. Tying security posture to compensation seems like a good way to incentivize workers to follow best practices, but it also leads them to deny responsibility and minimize mistakes when they're found. ®

TiDB Breach Exposes Flawed Cloud Security Assumptions

news Dark Reading · 2026-10-21 · ↗ original

A breach of an open source database provider may have inadvertently highlighted a serious gap in the way companies think about their cloud security.

On Oct. 19, software maker PingCAP, which sells an SQL database program called TiDB, disclosed that it had been breached. According to PingCAP's website, it serves major American corporations like Atlassian, Square, and Pinterest, as well as major players in China's artificial intelligence (AI) space, including Manus, Kimi, and more.

The perpetrator — the somewhat deceptively named "Fulcrum Security," or FulcrumSec, for short — is a relatively new extortionist group whose leak site already includes major organizations like LexisNexis, Novo Nordisk, and the Manchester Airports Group (MAG). Earlier this fall, FulcrumSec appears to have compromised PingCAP, enjoying something shy of unfettered access to all of its cloud management, financial, analytics, storage, and other systems for a month or more.

Related:Marvell, Microsoft & Oracle Work to Standardize Data Center Hardware Security

The even bigger issue is whether the breach exposed downstream customers' sensitive data. Investigators are still working out the details, but early evidence suggests that customers may in fact be at some risk. Though their actual databases weren't breached, the information their vendor stored about them may have been enough to cause serious issues.

Dark Reading reached out to PingCAP for comment but the company did not respond at press time.

Vendor Breach Puts TiDB Customers at Risk

In a security notification published 12 days after first having discovered the incident, PingCAP acknowledged that hackers had access to its systems from Sept. 9 to Oct. 7. Using stolen service account credentials, the company wrote, the unauthorized party accessed internal company systems and then copied data and source code.

PingCAP's own third-party-assisted investigation found no evidence that attackers ran malicious commands or maintained persistent access in their systems, nor did they access any customers' databases. Instead, it said, the threat actors accessed customers' billing and other business data, such as contract terms and pricing, as well as various information pertaining to cloud accounts and product usage — email addresses, SQL editor text and errors, etc. They also exported a table with encrypted API keys, though investigators said the encryption protected the keys from actually being used maliciously.

FulcrumSec, however, painted a bleaker picture.

In a name-and-shame post to its leak site, the hackers claimed to be in possession of all of PingCAP's service management records, its financial records, its files stored within Google Cloud, Jira support tickets, customer relationship management (CRM) data, analytics data, source code, plus a four-year-long log of every connection every one of its customers ever made to the TiDB Cloud service.

Related:Cloud Security Alliance Survey Finds Data Loss Prevention Often Detects Data Loss Only After It Happens

Crucially, the hackers did not claim to have stolen any TiDB databases straight up. Instead, they indirectly obtained a wealth of potentially exploitable user data like those aforementioned API keys and other secrets, and potentially sensitive internal data exposed by cloud database commands.

The attackers fingered individual enterprises caught in the crossfire: brand name US companies like AirBnB and Booking.com, Asian corporate giants like Baidu and Fujitsu, and a few of the world's biggest video game companies, including Capcom, Konami, and Square Enix. Asia represented the biggest slice of the pie, with nearly 2,000 affected organizations in Japan, China, and Hong Kong, with another 500 from India.

Additionally, FulcrumSec said its unauthorized access lasted for nearly two months, not just one. It was so comprehensive and unthreatened that, in the meantime, they were able to stand up a mirror of PingCAP's own service management system. Instead of having to manually exfiltrate data, their replication feed automatically pulled fresh copies of the company's internal database every six hours, for 22 days.

Related:'AgentCorruption' Puts AWS Environments at Risk With Single Prompt

Claims made by threat actors must always be met with a degree of skepticism, and Dark Reading did not independently confirm FulcrumSec's. Still, the group does have some record of reliability.

Last summer, for example, the group breached Manchester Airports Group (MAG), claiming to have stolen 86GB of data. That data turned out to contain far more genuine personally identifiable information (PII) than MAG copped to, according to reporting by BleepingComputer. And whereas some hackers exaggerate their winnings, this case was something of the opposite: that initial 86GB claim in fact represented compressed data. The hackers clarified that the actual, uncompressed total stolen was actually 640GB.

Orgs: Be More Critical of Your Service Providers

Even if one were to completely ignore the hackers' account, and take PingCAP's more limited assessment as the truth, it would still represent a potentially serious risk to customers.

Arguably the most acute dangers — more than the broad customer data, or the API keys if they are in fact protected — lie in the less obvious exfiltrated data. This includes Jira tickets, SQL histories, and places where organizations unthinkingly leak internal data. For instance, when customers use their cloud-managed database services, they send commands to the vendors' servers, obviously. Those interactions can often carry corporate secrets, or sensitive data of many other sorts.

"Vendors don't typically set out to store secrets. However, customers often pass them over to use features built for convenience, and the data can settle in places few people think of as credential stores," Crystal Morin, senior cybersecurity strategist at Sysdig, explains.

PingCAP's SQL editor text and errors as an example, she says. "That's query history and error output, which is where secrets can accumulate when someone pastes a connection string to debug something on the fly," Morin adds. In FulcrumSec's name-and-shame post, for example, it highlighted exfiltrated SQL statements that listed in full view one medical clinic's roster of patients, and another's list of medical professionals.

Keeper Security chief information security officer (CISO) Shane Barney seconds Morin's point. "The PingCAP incident illustrates a daily reality in enterprise security: attackers do not need to compromise a customer's primary database directly if they can systematically harvest upstream credentials," he says. "In modern software-as-a-service (SaaS) ecosystems, customer metadata, API keys and diagnostic query logs routinely seep into vendor environments through everyday operational telemetry. When service account credentials or administrative API tokens are stolen from a provider, that aggregated operational data transforms into a road map for exploitation."

Barney emphasizes the importance of cloud security hygiene — such as rotating vendor-facing API keys, and eliminating hardcoded and long-lived secrets in developer workflows — and vetting one's managed service providers by demanding continuous third-party risk assessments and independent certifications and attestations such as SOC 2 Type II and ISO 27001.

Morin urges organizations to ask a few specific questions when vetting cloud providers. "Teams should seek to understand what customer-provided data the vendor retains and what its retention policy is. They should also ask whether they scan for secrets at ingest and redact what they find," she says. "Teams may also want to understand how service account credentials are handled, whether they’re short-lived, how they’re scoped, how often they rotate, and what detections fire on anomalous credential or account use."

And, she says, don't forget: "Inquire about breach notification, specifically the timeline and what triggers it."

Compromised eMudhra intermediate certificates

threat-intel Cisco Talos · 2026-10-21 · ↗ original

Cisco Talos is aware of eight intermediate certificates belonging to the intermediate certificate authority, eMudhra. Rather than possessing the mandatory 384 bits of pseudo-random security, several private keys evaluated single-digit and double-digit integers. This misconfiguration allows an attacker with the private key of any of the compromised intermediate CAs to impersonate any website or service. Six of the TLS certificates, trusted by Chrome, Mozilla, and Apple have been blocked by these vendors already. Two other certificates, used for codesigning by Microsoft, have also been blocked. Talos expects there will be additional patches available across a variety of technologies as software applications work to remediate the certificates’ exposure.

Following the disclosure, eMudhra has revoked the compromised certificates and stopped issuing new certificates under its G3 root.

Compromise details

The cause of this issue, originated during an April 30, 2025 key generation activity conducted by eMudhra under its emSign Root TLS CA - G3 and cross-signed Comodo AAA Certificate Services.  During a key generation ceremony for 24 subordinate CAs, a flaw in eMudhra’s key generation process created a second set of weak P-384 keys during a wrap/unwrap step. Those keys were mistakenly used for eight intermediate CA certificates. This flaw took the encryption from 384 bytes of entropy down to 3 – 8, making recovering the private keys trivial. CVE-2026-111943 

Unlike languages that defer entirely to external dynamic system libraries (like OpenSSL), the Go programming runtime implements its own X.509 chain verification engine in the standard library (crypto/x509). While Go usually queries platform certificates, several platforms or static container environments rely on embedded or legacy root certificate pools where certificate revocations are ignored. 

To eliminate exploitation across the entire cloud-native ecosystem including Docker, Kubernetes, Terraform, and Prometheus, the Go team designated the compromised certificates as a vulnerability, CVE-2026-111943, and released Go versions 1.27.3 and 1.26.10. 

 The fixed versions filter out chains containingthe SHA-256 hashes of the SubjectPublicKeyInfo (SPKI) for all eight compromised eMudhra intermediate certificates.

Impact

These compromised certificates could allow adversaries to impersonate servers and intercept or modify traffic. The impact of their exposure is far more than just web browsers. Other programs that check for TLS certificates might still be impacted since they may not check revocation lists. One clear example is related to virtual private networks (VPNs); these technologies will likely require software updates to mitigate the issue. Based on this guidance, Talos strongly recommends users update software using and handling TLS certificates as fixes become available.

Talos is actively monitoring the impact of these compromised certificates and has not seen any malicious incidents involving them in the wild yet (as of October 21, 2026 14:00 UTC / 10:00 a.m. ET).

Significance of this breach  

Public key infrastructure relies on trust being delegated through certificate chains: root CAs authorize intermediate CAs, which can issue certificates within the scope of their authority. An attacker who obtains an intermediate CA’s private key may be able to issue fraudulent certificates that clients accept, subject to the intermediate certificate’s constraints and each client’s validation controls. In this incident, six compromised intermediates were for TLS and two were for code signing.

 For TLS, an attacker able to intercept or redirect a connection could use a fraudulent certificate to impersonate a server and potentially read or modify traffic if the client still trusts the affected key and no applicable protection blocks it. Protections such as revocation, key distrust, certificate transparency enforcement, and certificate pinning can prevent or expose such an attack. Browser vendors have blocked the affected TLS keys, but other applications may rely on separate trust stores or validation paths:

Enterprise infrastructure and VPNs

Organizations should assess TLS-using software and appliances, including proxies, reverse load balancers, VPN clients, and gateways. Exposure depends on the certificate chain being validated and the trust store and revocation behavior in use. A stale or separately managed trust store may need an application, operating-system, firmware, or trust-bundle update; verify the required action for each product.

Software supply chains and CI/CD

Build runners and package managers may be exposed if they fetch content over TLS while still trusting an affected key and an attacker can intercept the connection. A fraudulent TLS certificate could enable registry impersonation, but it would not by itself bypass separate package integrity checks, such as lockfile hashes, checksums, signatures, or provenance controls. Assess the actual package-manager configuration and dependency path.

Industrial IoT and embedded systems

Review devices that use bundled or independently managed CA stores, especially where certificate revocation or trust-store updates may be limited. Some devices may require a vendor update or compensating control, but the necessary action depends on each device’s validation and update mechanisms.

Talos recommends updating affected software and trust stores as vendor fixes become available.

Meta on the spot for $25 billion under New Mexico privacy ruling

news The Record · 2026-10-21 · ↗ original

Meta must pay $25 billion in fines for data privacy violations related to the Cambridge Analytica scandal that became public almost 10 years ago, according to a New Mexico court filing released Wednesday.

In September, a jury found Meta had broken the state’s unfair practices law 43 million times for its role in the incident, which a whistleblower made public in 2018. Each violation carried civil penalties of as much as $5,000.

The state was initially awarded $220 billion, but state District Court Judge Francis Mathew reduced the penalty to $25 billion, according to the court filing. Meta will be charged 15% annual interest on the amount until the fine is paid off.

The case is tied to Meta-owned Facebook, which shared as many as 87 million users’ data with the Cambridge Analytica. The British political consulting firm then used the data to create psychological profiles of voters to facilitate targeted advertising, including in the 2016 presidential election.

New Mexico’s litigation focused on what Facebook told consumers about its data practices and how it combats misinformation and hate speech in the wake of the scandal becoming public, according to a press release from the office of Attorney General Raúl Torrez.

“The scale, duration, repetition, breadth, and willfulness of the violations, together with the evidence concerning Facebook's internal knowledge and practices … constitute substantial aggravating circumstances,” Mathew wrote in the filing.

Mathew highlighted the fact that senior Facebook leadership, including CEO Mark Zuckerberg and then-COO Sheryl Sandberg, created a calculated strategy to mislead consumers by among other things overseeing the creation of materials they called a “song sheet” to coordinate a public relations response.

“Facebook continued making public representations concerning users' control of data, third-party data misuse, misinformation, hate speech, and equal enforcement after employees, researchers, and senior personnel had internally identified that Facebook could not make good on its public promises,” the filing said, noting that Zuckerberg was aware of the deception.

The platform knew at the time that information regarding its data access infrastructure and enforcement protocols were not verifiable by users and the company took advantage of that, the filing said.

Facebook also failed to follow through on the “comprehensive” probe it promised consumers after the scandal became public, Mathew said. 

The social media company was “aware at the time it made the promises that it did not have the ability to conduct such a thorough investigation or enforce deletion of the data due in large part to Facebook's poor record keeping and failure to vet third party developers at the time they were granted access to user data,” the filing said.

Pressure from senior leadership to minimize costs, a weak enforcement mechanism, poor investigative techniques and a focus on not setting a precedent for future probes caused Facebook to use an App Developer Investigation that was “willfully ineffective,” according to Mathew.

The ruling and Torrez’s approach to the enforcement “makes it all but impossible to do business in the state of New Mexico,” Meta Chief Legal Officer C.J. Mahoney said in a statement.

“At its core, this lawsuit seeks to impose a tax on speech to enforce new rules for what people can say online.” 

Meta plans to appeal the ruling, the statement said.

Torrez won $375 million in damages from Meta in March after a jury found the tech behemoth broke state law related to its kids’online safety practices.

Meta has already faced steep fines related to the Cambridge Analytica scandal, including a $459 million penalty that was included in a roughly $17 billion August settlement with a group of several other state attorneys general pursuing the tech giant for its child safety practices.

Printerpix and the not so private photo album

red-team Pen Test Partners · 2026-10-21 · ↗ original

TL;DR 

  • Printerpix store their uploaded files in an S3 bucket 
  • The S3 bucket is publicly accessible and has indexing enabled 
  • This allows uploaded photos to be enumerated and viewed by any Internet user 
  • Disclosure was difficult as the only interface was one customer services email address 
  • Vulnerability was silently fixed around 70 days after disclosure 

A bucketful of photos 

There are many services that allow digital photos to be converted to prints. These include a plethora of other printing services so that customer photos may be converted to picture books, mugs, magnetic photo tiles, clothing or even a throw. 

With the combination of destination, these services allow photos to manipulated in their web frontend, to be rescaled and altered to better fit the output. 

It was noticed that whilst using one of these providers, Printerpix, all photos were uploaded to an S3 bucket and then were loaded directly from the bucket to aid in the scaling and manipulation of images. 

Out of curiosity the bucket’s home was visited and it was noticed that the bucket allowed indexing, meaning that all the files stored in the buckets could be identified and the files downloaded. 

Technical details 

A bucket is a cloud-based storage concept – it is a place where files can be placed and retrieved by their key. The concept maps closely to a filesystem with a directory and filename which is referred to as a “key”. This makes it very easy to integrate cloud storage into an existing process. 

Buckets from all major providers can also have temporary access tokens which are signed to that specific key and request. This allows a security method to allow the upload and download of files with access restricted to one individual request. 

An alternative is to allow the bucket and key to be open to the public, which allows any user with the exact key for the file to access it through a web browser with no parameters. 

A bucket may have indexing enabled, this means that if a directory key is provided than the contents of that directory can be indexed, so that all keys in that directory can be viewed and can then use that key to access the file directly. 

When a file is uploaded to Printerpix, there is a set of standard requests: 

First a POST request to /designer-q/ which details the image size, a JSON file is returned which contains the S3 key and upload URL for this image, this upload URL has an access token and is signed so can only be used by this request.  

Notice the value of x-amz-acl in the JSON response. A PUT request is made to the provided upload URL that uploads the raw image. 

Later requests included a GET request to the bucket with the key for that image: 

This identified that the bucket used could be accessed through the URL: https://storage-ssd-01.printerpix.co.uk/userfiles 

Visiting that URL showed that indexing was open, which returns an XML document listing all the keys for all files stored within. By default AWS S3 will only show a maximum of 100 keys, but as the files date back to 2021, it was estimated that there were millions of files within the bucket. 

As the index could be accessed, the keys could be obtained and used to access the contents of the images. 

Reporting and disclosure 

The disclosure timeline is below: 

11/08/2026: Initial disclosure 

11/08/2026: Received generic “thank you response” 

20/08/2026: Reminder sent 

07/09/2026: Received a response with a named member of the support team, a ticket number was generated 

11/09/2026: Second reminder sent 

11/09/2026: Received generic “thank you response” 

14/09/2026: Further details sent including URLs to demonstrate vulnerability 

14/09/2026: Received a statement that “I would like to reassure you that Printerpix customers’ personal data and photographs are safe and are not accessible or downloadable by others. Customers cannot access another customer’s account, projects, or photographs through the Printerpix platform.” 

14/09/2026: More details sent 

15/09/2026: Received an email for another person’s problem 

15/09/2026: Received an apology for the previous email 

15/10/2026: Third reminder sent 

20/10/2026: Checked current status and identified that it had been resolved, was not notified by Printerpix. 

21/10/2026: Decided to publish as the vulnerability has been fixed

Disclosure was an interesting exercise, Printerpix had neither a security contact, a security.txt file, a security DNS record or subscribed to any bug bounty program. The only contact details on the website was a generic contact us email address at [email protected] 

Being sent an email for a different customer shows serious failure in managing the customer support mailbox, although there was nothing confidential in the email, just a first name it was concerning. I received an apology for this, but I wonder whether the other customer was notified. 

Advice 

Using cloud features like buckets is an attractive option for quickly rolling out a product with lots of potential flexibility, but ensure that security features are used to protect any data stored within the cloud. 

In this case, the developers knew about S3 access tokens and signing as they used them for the upload process, but at some point, a decision was made to make the images publicly accessible. Even then, complex filenames were used so that risk would have been minimised except that indexing was enabled on the bucket. 

This strongly suggests that the product has not been fully pen tested to identify all security risks. This is a trivial to exploit vulnerability that any technical user who followed the upload process could have identified. 

Printerpix resolved the vulnerability by migrating to a different cloud provider and seems to have configured the permissions on the new store to be more secure. At this point we decided to publish, as the vulnerability had been fixed. 

The vulnerability disclosure was on par with companies that do not have a security function. Adding a security contact email address, a security.txt file or even a security DNS record are simple actions that can allow security researchers to disclose responsibly and reduce the length of time a vulnerability is open. 

A lack of dialogue with the researcher was also a concern, that we weren’t told that it had been resolved showed a concern over how customer data was being managed. 

There are other concerns with Printerpix’s use of cookies, ad tracking and communication to third parties that seem to ignore the state of the cookie dialogue box, that could make for future vulnerability disclosure.
