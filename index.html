Nvidia picks OpenShell to tame AI gents

news The Register · 2026-10-21 · ↗ original

Nvidia has proposed a new way to keep corporate AI agents in line. Nvidia on Wednesday introduced its OpenShell Reference Architecture. Based on the company's OpenShell secure runtime, It's a recipe for creating, operating, observing, and policing AI agents using OpenShell on Nvidia hardware. "Nvidia created OpenShell to give agents the freedom to do useful work within clearly defined boundaries — contained, monitored and under control," CEO Jensen Huang said in a canned statement. "With the OpenShell Reference Architecture, agents can think on Rubin, act on Vera and be governed on BlueField." AI agents are touted as a powerful automation technology. The reality is that they can be unruly, as demonstrated by security testing OpenAI and Anthropic conducted, during which their models exceeded their remit and attacked third-party organizations. Developers of existing agents, like Claude Code, Codex, OpenClaw, and OpenCode, therefore include controls that limit access to tools like curl and bash.Devs also create sandboxes to isolate an agentic process from the host, so that if agents go awry they're contained. OpenShell sits a level above that with a runtime that extends sandboxing to govern gateway-brokered credentials, identity and policy boundaries, and (eventually) routing and workflows too. At least mostly – OpenShell still has a few open security-related issues listed on GitHub. To implement OpenShell, organizations need Nvidia hardware. The company's blueprint calls for Nvidia Vera Rubin infrastructure to run models like Nvidia Nemotron, with agent harnesses handled via Vera CPUs, and Nvidia BlueField-4 DPUs (aka SmartNICs) propping up Nvidia Sentry security software to monitor agent behavior. The AI biz has made this blueprint available to partners capable of powering Linux and Kubernetes infrastructure. The usual suspects are aboard: Canonical, SUSE and Red Hat. Cloud hyperscalers Amazon Web Services, Google Cloud, and Microsoft Azure have also been tapped as vendors for this vision. And of course Nvidia's floor plan applies to agents from various model builders, including Anthropic, Cohere, Google, Meta, OpenAI, Perplexity, Reflection, and SpaceX. Nvidia says several banks – Europe’s BBVA and Santander – are perusing the OpenShell Reference Architecture spec to see how it aligns with their security and governance requirements. And the AI biz is not too modest to let slip that SAP is integrating the OpenShell Reference Architecture with its Joule Studio runtime for safer agent operations. It's worth noting that OpenShell collects telemetry data by default, "to improve the project," Nvidia insists. The biz allows users to opt-out, with a cautionary note: "Third-party services, model providers, inference endpoints, agents, or tools that you configure and use with OpenShell may have their own terms and privacy practices." ®

Browsers Block eMudhra Intermediate CAs Over Recoverable Private Keys

news SecurityWeek · 2026-10-21 · ↗ original

The private keys associated with eight intermediate certificates issued by Indian certificate authority (CA) eMudhra have been compromised, and root programs and trust stores have started blocking them.

The certificates were issued in April 2025, and some of the compromised keys could allow attackers to generate fraudulent certificates and impersonate any website.

On October 17, Mozilla and Google blocked the certificates in Firefox and Chrome. Apple and Microsoft blocked them on October 19 and October 20, respectively. Sectigo took revocation steps too, and Cloudflare patched its services.

eMudhra revoked the compromised certificates, and the issue was communicated to downstream trust stores.

“The private keys for these certificates were generated with insufficient randomness (i.e., weak cryptographic entropy), enabling anyone to forge trusted HTTPS certificates to impersonate any website against clients that have not yet removed trust in those CAs,” Google explains.

Although the certificates have been blocked and revoked, some clients may require software updates to ensure that the compromised intermediates are no longer trusted.

Advertisement. Scroll to continue reading.

Mozilla’s Dennis Jackson has published a tool to check whether clients still trust the compromised certificates. He also explains that the private keys were incorrectly generated and could be retrieved from the certificates.

In fact, Jackson warned that several individuals have independently retrieved the keys, as the process is fairly easy and fast.

“The private keys are effectively all-zeroes apart from the last byte. They can be recovered near instantly via the baby-step giant-step discrete log algorithm,” Jackson said.

There appears to be no evidence in Certificate Transparency (CT) logs that the keys were used maliciously before revocation, but not all clients enforce CT, and threat actors may have used them to impersonate those clients.

According to eMudhra, a flaw in the script used during the key generation ceremony created a second, weaker key pair, which was mistakenly used to create the certificate signing requests because its labels were similar to those of the original keys.

“Some additional context – these issuers created were meant for export to our US and European data centers to solve data sovereignty issues for some of our customers (but never ended up operationally in production except for one),” the CA said.

“There were human errors in multiple steps of the process that resulted in significant flaws in the key lifecycle integrity process for this KGC. We are now digging deeper for code flaws, process gaps, and maker/checker controls specific to this issue. Over the next week, we will reverify every key ceremony we have done,” eMudhra added.

PHP2Shell: What Actually Protects You Before the 14:00 UTC PHP RCE Patch, and What Doesn't

news The Hacker News · 2026-10-21 · ↗ original

You cannot fully block the two critical PHP flaws called PHP2Shell before today's fix, and the one setting being passed around as a workaround is not enough on its own, the security firm that suggested it now says.

PHP will release the fix at 14:00 UTC on October 21 for two flaws it rates 9.2 out of 10, and has given no workaround of its own. Until you can install it, what lowers your risk is taking exposed PHP off the internet or behind access controls, cutting what a compromised server can reach, and having the update ready to apply the moment it lands.

No attacks have been reported. PHP has not said which versions are affected, which part of PHP is involved, or whether any setting changes the risk; it says the full details and the fixed versions come with the release.

At the time of writing, that release was not yet out. So nobody outside the group that found the flaws can test whether a given defense works, which is why the advice below is about lowering risk, not promising safety.

The setting you were told to change is not protection

The workaround spreading on social media and security blogs is one line in a PHP configuration file: session.upload_progress.enabled=0. It turns off Session Upload Progress, a PHP feature that's enabled by default, which records how far a file upload has progressed so another request can check on it.

GMO Flatt Security, a Tokyo security firm, suggested setting it early on October 21, saying it could not be sure the change fully addresses the flaws but thought it would help with some probability.

Later the same day, the firm walked that back. In an update timestamped 14:00 Japan time (05:00 UTC), it said the setting alone is not a complete fix and that attacks getting around it are expected. It told administrators to prepare their update, watch for attack traffic before the release, and apply the fix as soon as it is out.

A PHP core developer said the same thing more bluntly. Replying to someone who suggested the upload-progress setting might patch the flaw, Gina Peter Banyard, a PHP core developer and documentation writer funded by the PHP Foundation, wrote: "The only thing I can say is that the only mitigation is patching/upgrading PHP. I sadly know too much."

The setting cannot be relied on for two reasons. GMO Flatt expects a way around it but has not said what that is. And the whole idea that the flaw lives in Session Upload Progress is a guess: PHP has not confirmed it, the firm itself said it holds only so far as its own research matches PHP2Shell, and an independent code audit argues the specific bug others describe in that feature does not exist in released PHP. That audit is from an anonymous account and PHP's own code will settle it, but it is one more reason not to treat the setting as a shield.

Not everyone agrees. One vendor, Upwind, still lists the setting as an immediate mitigation, passing along another researcher's analysis rather than its own tests. watchTowr, which reproduced one of the flaws, says there is "no confirmed patch or workaround at this time."

If you already set it

No one is telling you to undo the change. The instruction is only not to count it as protection. PHP's own manual already advises turning the feature off where an application does not use upload progress bars, because the stored file names and field names "are not validated and may contain PHP code." If you turned it on by mistake somewhere that needs it, the only cost is that upload progress bars stop working.

Check that the change is actually in effect on the process that serves web traffic, not on the command line. The setting is INI_PERDIR, so it can be set in php.ini, .htaccess, or .user.ini.

A .user.ini file is read-only by the CGI and FastCGI versions of PHP, not by the Apache module, and PHP re-reads it only every 300 seconds by default, so a change there can take five minutes to apply.

Under the Apache module, use .htaccess or the server config. Confirm the value on PHP-FPM or mod_php, whichever serves your site, not on php -i at the shell.

If you can patch at 14:00 UTC

Get ready now. GMO Flatt's advice is to confirm your update steps and the checks you run afterward, rehearse any config change, and line up the people and approvals for a possible emergency restart. When the fix lands, update the runtime that serves web requests, which is PHP-FPM, mod_php, or CGI, not the application on top of it.

PHP issues fixes only for its four supported branches, 8.2 through 8.5. Which exact versions carry the fix and how far back the flaws extend will be announced with the release.

The Hacker News reported the branch support and the wider background in its earlier coverage of the disclosure.

If you cannot patch at once, or run an unsupported version

Where an immediate update is not possible, CERT-EU advises organizations to "consider isolating internet-facing applications from public networks until a fix can be applied." Banyard put the same point from inside the project: turning a server off for a day "might be the most sensible thing to do.

But that is far from a reasonable thing to demand for most people." Short of shutting down, restrict reach: put the site behind a VPN, allowlisted clients, or authenticated access at the edge, and check that traffic cannot reach the origin directly around those controls.

Shrink what an attacker gets if the server is taken over. GMO Flatt's other steps are to reduce the data stored on the server, reduce its privileges, remove stored credentials, including cloud roles, and ensure logging is enabled and kept in a secure location so you can investigate later.

Branches older than 8.2, including 8.1, 7.x, and 5.x, are end-of-life and receive no PHP fixes. For those, upgrade, take the system offline, or isolate it; a Linux distribution or hosting provider may backport a fix on its own schedule.

A web application firewall is a weak stopgap here, not a fix. Cloudflare added emergency "anomalous execution" rules on October 21, but its changelog names neither PHP nor these flaws; such rules only see traffic that passes through the provider, and they can miss variants.

If someone else runs your PHP

Updating WordPress, Laravel, or another application does not update the PHP runtime underneath it; that comes from your server package, host, or container image. On managed or shared hosting, ask your provider when a fixed PHP build will land and have them stand by.

Hosting providers build their packages only after PHP ships the fix: CloudLinux, for one, says its updated packages depend on the upstream release and will be posted when ready.

What to check when the release lands

No exploitation had been reported: watchTowr's FAQ listed none as of October 21, and these flaws were absent from CISA's catalog of known exploited flaws when it was last checked.

A short demonstration video was posted and then removed, and the audit above states that the circulating proof-of-concept code does not fire. Treat that as a snapshot that can change.

When the fix ships, check the fixed version for your branch, which versions PHP lists as affected, whether PHP confirms or rejects any setting as a mitigation, and whether the session code changed, which also answers the dispute over where the flaw lives.

The fixed versions and the advisory will appear on php.net and through PHP's GitHub security advisories, where the project assigns its own identifiers. After updating, review your logs for anything that happened before you patched.

CISA: SafePay ransomware hit over 600 critical infrastructure orgs

news BleepingComputer · 2026-10-21 · ↗ original

The Cybersecurity and Infrastructure Security Agency (CISA) says the SafePay ransomware gang has breached over 600 critical infrastructure organizations worldwide since 2024.

In a joint report with the FBI, the U.S. Secret Service (USSS), Germany's Landeskriminalamt Rheinland-Pfalz, and the UK's National Crime Agency and North West Regional Organised Crime Unit, the federal agency added that paying ransoms does not guarantee recovery of files encrypted in ransomware attacks and urged victims to report incidents to law enforcement.

"SafePay is one of the most active ransomware groups and have affected businesses and critical infrastructure in North America, South America, Europe, and Australia—including at least 600 organizations from multiple critical infrastructure sectors since August 2024," CISA said.

"SafePay threat actors gain initial access through a variety of means, including credential exposure, brute force password attacks, and exploiting virtual private network (VPN) access—particularly the IP addresses of VPN provider 'Mullvad'."

The co-authoring agencies advised network defenders to secure their networks against the ransomware group's attacks by restricting administrative tools and privileges to block lateral movement after compromise and implementing multifactor authentication (MFA) and identity, credential, and access management (ICAM) policies for better account security.

Security teams should also keep systems updated, focusing on flaws affecting VPNs, firewalls, and other edge devices added to CISA's catalog of actively exploited vulnerabilities because they're often targeted in SafePay attacks for initial access to victims' networks.

"They also use phished account profiles to infiltrate networks and exploit common vulnerabilities and exposures (CVEs) for edge devices and other internet-exposed systems through automated scripts," CISA added. "SafePay actors may disrupt recovery operations by deleting shadow copies and resetting network-attached storage devices containing backups."

The advisory also includes indicators of compromise (IOCs) and tactics, techniques, and procedures (TTPs) to previous SafePay ransomware activity observed between November 2024 and August 2026 during FBI, USSS, and Landeskriminalamt Rheinland-Pfalz investigations.

Unlike similar operations, ​SafePay emerged in August 2024 as a private ransomware group that doesn't work with affiliates. 

It has since added hundreds of victims from North America, South America, Europe, and Australia to its dark web leak site, but the actual number of victims it has breached and attempted to extort is higher, since it lists only those who don't pay on its leak platform.

This ransomware group is also known for double-extortion tactics, stealing sensitive documents before encrypting the victims' systems and threatening to leak all the stolen data online if a ransom isn't paid.

Since the start of 2025, SafePay has slowly filled the gap left by BlackCat (ALPHV) and LockBit ransomware, becoming one of the most active ransomware operations.

Overall prevention scores can hide what happens after initial access. Once attackers are using valid credentials, prevention drops sharply.

California warns all public school students of data stolen in contractor breach

news The Record · 2026-10-20 · ↗ original

A cyberattack on a contractor for California’s Department of Education (CDE) exposed troves of sensitive information covering all children enrolled in public schools over the last three years.

The CDE released multiple statements over the last week warning the state’s students that assessment contractor Educational Testing Service (ETS) suffered a months-long data breach.

The student information copied by hackers includes:

  • Student names, dates of birth, residential addresses, schools, districts, and grade levels;
  • Statewide Student Identifiers (SSID) and local student identifiers;
  • Gender, race or ethnicity, primary language, country of origin, and English learner status;
  • Disability and Section 504 status, testing accommodations, and primary disability type;
  • Eligibility status for the following programs: Title I, Part A; Title I, Part C; McKinney-Vento; and Military Connected Student; and/or
  • English language proficiency information and statewide assessment registration, participation, and results, where applicable.

Those affected include current and former students enrolled in California public schools between 2023 and the current school year, as well as students who left a California school since 2006 and did not confirm transfer to another school with the CDE.

CDE hired ETS to provide testing to California K-12 public schools, which enrolled more than 5.7 million students in the 2025 school year. ETS manages the California Assessment of Student Performance and Progress (CAASPP) and the English Language Proficiency Assessments for California (ELPAC) exams given each year. 

ETS, which did not respond to requests for comment, said in a release that hackers copied student information through a secure file transfer protocol site this year from May 22 to September 18. 

After discovering the breach on September 25, ETS initially disabled the account used to steal the information and eventually took the entire site offline before building an entirely new platform in response to the hack. 

“After working with law enforcement and cybersecurity experts, ETS has taken steps to reduce the potential risk of the data being made publicly accessible,” CDE said. “Furthermore, ETS, following regular web monitoring, has, to date, not uncovered any evidence that the information has been made public.”

A spokesperson for CDE declined to explain what steps ETS took to reduce the risk of the data being made publicly accessible. The ETS statement claims it worked with “law enforcement as well as with cybersecurity experts” to reduce the risk of the incident. 

No hacking group has said it was responsible for the attack as of Tuesday. 

The state began notifying families of the incident on October 16 and said it will continue to distribute notices of the attack through November. 

CDE said it is working with state cybersecurity experts and other agencies to assess how the incident will impact California students. They are also “reviewing… ETS’s compliance with applicable data security and contractual requirements.”

ETS said it has “halted normal enrollment data processing and paused certain testing activities while the security of its systems are assessed, and the investigation continues.” CDE explained that it is working to minimize the disruption and resume the affected testing as soon as possible. 

Educational service providers like ETS have been repeatedly targeted by cybercriminals – with multiple incidents impacting large companies like PowerSchool, Instructure, Illuminate Education, McGraw Hill, Kaplan and more.

There's only so much code: the rise in vulnerability numbers

threat-intel Cisco Talos · 2026-10-20 · ↗ original

  • Frontier AI models (like Mythos) are rapidly mining decades of technical debt across ubiquitous legacy libraries, driving monthly Microsoft Patch Tuesday vulnerability advisories up more than tenfold (reaching 1,415 this month). This volume is overwhelming open-source maintainers and putting pressure on the traditional 90-day coordinated disclosure model. 
  • Despite a 105% year-over-year surge in CVEs, Known Exploited Vulnerabilities (KEVs) grew by only 37%, and only 3 of September's 975 Microsoft advisories saw in-the-wild exploitation, demonstrating that the vast majority of AI-discovered bugs are not practically exploited. 
  • We may be able to take new-bug-class vulnerability spikes as evidence that these vulnerabilities will eventually level off and decline, once the historical code backlog is remediated and AI verification is embedded directly into new development pipelines. 
  • With attackers able to parse patches faster via AI, defenders cannot cover for all possible threats. Organizations should continue to build robust defense-in-depth. Prioritize high-exploitability flaws in their specific environments, implement interim mitigations (such as LiveProtect), deploy behavioral anomaly detection, and integrate current AI evaluation models into their software build chains. 

The September Microsoft Tuesday release included 975 vulnerability advisories. This month, 1,415 vulnerabilities were just dropped. Compared to a pre-June average of 100 a month, that increase is staggering. Where did they come from? 

As of April, frontier models came onto the scene more fine-tuned than ever toward vulnerability detection, particularly with the introduction of Mythos. The deluge brings a lot of questions: 

  • If these numbers are real, why hasn’t the internet collapsed? 
  • Are these vulnerabilities a new breed, and if not, why didn’t analysts find them in code that is sometimes decades old? 
  • Is the coordinated disclosure model still relevant in an era of this kind of speed? 
  • How in the world do defenders deal with those numbers? 
  • Should we go home, kiss our spouses, and prepare for the end? 

The answer to many of these questions boils down to this: The majority of these vulnerabilities are coming from repositories of old code from large-profile products and systems; and disclosure does not equal weaponization. 

Where is it from? 

AI is chewing through a backlog of technical debt in libraries and tools used as the dependable, best-practice lynchpins of so many environments. These models have a new perspective, an ability to "think" without some of the hangups or assumptions of human defenders, and they are thorough in listing those vulnerabilities. 

Entrenched older tools have always been prime targets because of their predictability; attackers know those tools and all their secrets, and they know what is likely to be present in a network with them. Multi-exploit attacks can be deployed with little variability.  

Pre-Mythos threat actors exploited log4j (CVE-2021-44228) to immense success. The library was ubiquitous, included in nearly every environment, but not a component that got cataloged in visibility scans. A combination of scale and low visibility meant defenders were blindsided, scrambling to find out if they even used the log4j library before starting to concoct a mitigation plan. 

Talos has ongoing relationships with some of the largest technical vendors (such as the Microsoft Active Protections Process (MAPP) agreement). Organizations share additional information—detection guidance or maybe a POC — for vulnerabilities that are most likely to be exploited, to enable Talos to provide adequate coverage when the advisories are announced.  "Microsoft believes it is important for us to provide detection content, based on their guidance," as Yves Younan, Director of Talos Vulnerability Discovery, Detection, and Testing, says.  

Talos has needed to invest more resources to get coverage in on time for critical vendors like Microsoft to keep up with notifications coming in fast and often on staggered or out-of-band timelines. 

For larger vendors, the pressure is handleable for now. However, open-source projects are getting flooded. Some projects have a trusted group that can combine to tackle patches, and some share with the full community for immediate assistance, but it is up to the project. The internet runs on open-source work. 

The pace of discovery presents a challenge for the traditional coordinated disclosure system vulnerability hunters have been using for years, and some are calling it into question.  

Security vulnerabilities should be reported, to enable an informed defender base and regular patching, and vendors responsible for vulnerable code need time to create coverage. A timed disclosure model where notifications are sent to a vendor, who then has a set period of time (typically 90 days) to provide coverage before the disclosure is released publicly, has created a more secure online environment for decades.  

Now, many practitioners are releasing advisories publicly without a disclosure period beforehand. The reasoning is that if one AI can find a weakness, any other could, so the vulnerability is already, effectively, released.  

This conversation is actively changing expectations around vulnerability disclosure, and guidance is in flux. 

Will it stay this high? 

No one knows the future, but we can always look to the past for insight.  

Numbers of vulnerabilities jump drastically when a new bug class is identified, as their possibilities are explored to the fullest. Then the discoveries plateau and drop off. 

When format string vulnerabilities were discovered as a new bug class in 2000, the initial influx of discoveries ramped up and up, until reaching a peak in 2005 and then slowly declining over the next couple of years. Format string vulnerabilities are still discovered, but they are a smaller overall fraction of the number of CVEs discovered in a year.  

Theoretically, AI-assisted vulnerability discovery could go the same way.  

While frontier models have not discovered a new vulnerability class, they are more efficient at discovering known types of software vulnerabilities. Given that a lot of vital software has a long history of code releases, there’s plenty of code to mine for weaknesses. But there’s only so much code… right? 

Old and commonly used tools are often under the highest scrutiny, lending them one kind of safety: Because of their popularity, utility, and stability, when popular tools have vulnerabilities, they are discovered fast and patched promptly. 

As the historical backlog of essential systems is turned over by AI, vulnerabilities will be found and patched. New code will ideally be run through AI bug-checkers that will prevent new vulnerabilities from being introduced. The rate of new vulns should level off and drop accordingly.  

There are some caveats. In the past, as vulnerability disclosures increased through coordinated disclosures, we saw increased adoption of mitigations. Exploitation became significantly harder. Attackers often need to chain together 3 or more vulnerabilities to successfully exploit a system.  

However, more awareness of vulnerabilities often leads to more exploitation. Attackers often use vendor patches meant to protect customers to discover where vulnerabilities might exist. The frequency of patching has delayed human attackers via parsing bottlenecks, but AI can eliminate that problem.  

Are the numbers the real issue? 

The volume is certainly up.  

Fresh as this blog is being finished, the October Patch Tuesday dropped almost 500 more than last month. 

With refinement, any vulnerability could become a link to a path of effect. But... not all vulnerabilities are exploitable. Some are wildly impractical for attacker use. In fact, the percent of Known Exploited Vulnerabilities (KEVs) is vastly smaller than the found vulnerabilities.  

Of the 975 vulnerabilities Microsoft reported in September, there were only three in-the-wild exploits detected. When viewed by percentage, vulnerabilities versus KEVs tell a different and perhaps reassuring story. 

Compared with the same period last year, additions to the known-exploited vulnerability list increased by 37%, while published CVEs increased by 105%. However, we wouldn't necessarily expect those figures to grow in proportion. Adversaries only need enough useful vulnerabilities to compromise their targets, and the same vulnerabilities can be reused against many organizations. The KEV count tracks distinct vulnerabilities known to be exploited, not the number of attacks or successful compromises. 

AI helps ingest code, advisory reports, and attack surfaces with inhuman speed, but it cannot currently make judgment calls about the value of a weakness. 

For defenders, the question remains the same: Which vulnerabilities provide a viable path into their environment, and how do you close those paths?  

What do we do now? 

The undeniable danger here is in exploitation time going down rapidly, while the vulnerabilities that could become exploits is still going up. The biggest hurdle for a defender is determining what is a real vulnerability for their environment, and what is not.  

Different defenders have different forms of control depending on their role.  

For those who are writing code, the new standard validation chain should include AI evaluation by models at least as up to date as those being used to hunt for vulnerabilities. It is relatively cheap to run new code through AI, but very expensive to run a cumbersome backlog of old code through. Bite it off in chunks. 

For those whose role involves keeping the tools ready: Upgrade ASAP.  Don't stop there.  

  • For Cisco customers, implement LiveProtect to mitigate vulnerabilities between advisory release day and patching, to give time for that patching. Do this for everything you own. 
  • Move beyond static domain blocking and implement behavioral detection that alerts on anomalous traffic patterns directed toward automation platforms. 
  • Hone your focus to the vulnerabilities with the highest exploitability in your environment. KEVs are far less common among the sea of advisories, and their numbers have not risen proportionally with the AI-assisted deluge. 
  • Focus on building defense-in-depth. Employ multiple protection systems, to cover for delays in patching. Implement interim mitigations (such as LiveProtect), create custom IPS/Snort triggers to block pre-patched traffic using SnortML, deploy behavioral anomaly detection, and integrate current AI evaluation models in software build chains.

CVE-2026-106173 Deep-Dive: FortiSIEM gRPC Path Traversal File Write RCE

red-team Horizon3.ai · 2026-10-20 · ↗ original

On 13 October 2026, Fortinet published a security advisory for a critical vulnerability affecting their FortiSIEM product. The vulnerability, CVE-2026-106173, allows for an arbitrary file write by abusing an issue in a gRPC service.

Horizon3 is no stranger to the FortiSIEM. We’ve disclosed several critical vulnerabilities through the years that you can catch up on:

  1. CVE-2023-34992: Fortinet FortiSIEM Command Injection Deep-Dive
  2. CVE-2024-23108: Fortinet FortiSIEM 2nd Order Command Injection Deep-Dive
  3. CVE-2025-64155: Three Years of Remotely Rooting the Fortinet FortiSIEM

All of our prior research has involved the same component, the phMonitor service which listens on port tcp/7900. This latest advisory details a new service that we had never looked at, a gRPC service on port tcp/27918. Given our familiarity and the intrigue of a new service to look at we dove in.

Reaching the Vulnerable Service

Looking at the listening services on the FortiSIEM, we find that phQueryMaster is bound to tcp/27918. The phQueryMaster service stands the gRPC server up in grpcNotificationServer::run(). The listen port comes from the command_port config value (7918), which is passed through phSecureUtils::getGrpcPort() and mapped to tcp/27918; the address is built as [::]:27918, so the service binds every interface.

// grpcNotificationServer::run()  (libphGrpcServices.so)
unsigned short port = mServerPort;                                 // command_port = 7918
std::string addr = "[::]:" + phSecureUtils::getGrpcPort(port);     // [::]:27918
grpc::SslServerCredentialsOptions sslOps;
// sslOps.client_certificate_request stays 0 == GRPC_SSL_DONT_REQUEST_CLIENT_CERTIFICATE
auto creds = grpc::SslServerCredentials(sslOps);               
builder.AddListeningPort(addr, creds, 0);                    
builder.RegisterService(&svc);
builder.BuildAndStart();

Sometimes, gRPC servers can require client certificates for authentication, but here there server sets that option to false. This means any remote client can connect to the gRPC service on port tcp/27918 unauthenticated and without presenting a client certificate to reach the vulnerable gRPC service.

The Path to Arbitrary File Write

Now that we’ve found the vulnerable gRPC service, we inspect the available RPC methods and find SendQueryResult.

message QueryResultReq { bytes file_content = 1; }
service phoenixSvc { rpc SendQueryResult(stream QueryResultReq) returns (PhoenixReply); }

SendQueryResult’s handler parses four values from the received message: query-id, src-ip, period-start, and period-end. The handler then constructs a file path with the lightly formatted src-ip and query-id.

// grpcNotificationService::SendQueryResult  (grpcNotificationService.cpp)
replaceString(srcIp, ".", "_");                         
std::string fileDir = "/query/result/" + queryId;       
if (!phMiscUtils::DirExists(fileDir.c_str()))           
    phMiscUtils::mkdir(fileDir.c_str());               

Bug #1 is that fileDir is built by string concatenation with an attacker controlled value, without any input validation. A query-id of ../../../../../tmp/x allows an attacker to traverse outside of the query directory. So an attacker has arbitrary directory control.

The filename itself is also partially attacker controlled, result-<srcIp>-0-0-<id>.dat, and the streamed bytes that follow will be the files contents.

std::stringstream path;
path << fileDir << "/result-" << srcIp << "-"
     << periodStart << "-" << periodEnd << "-"
     << mGetQueryResultUniqId() << ".dat";              
std::ofstream output;
output.open(path.str().c_str(), ios::binary|ios::out|ios::trunc);   
while (reader->Read(&req))                              
    output.write(req.file_content().data(), req.file_content().size());           

So ultimately, an unauthenticated attacker can write arbitrary data into an arbitrary directory, but with a limited filename. The minimal request is one gRPC SendQueryResult with this metadata:

query-id:     ../../../../../tmp/fortisiem-cve-2026-106173
src-ip:       127.0.0.1
period-start: 0
period-end:   0

which creates /tmp/fortisiem-cve-2026-106173/result-127_0_0_1-0-0-<id>.dat containing the streamed bytes.

Exact Filename Control

The path traversal lets an attacker choose the directory a file lands in, but not its exact name: the server always tacks on its own ending, result-<src>-<start>-<end>-<id>.dat, where <id> is a counter the server controls and the request can’t set. On its own, your stuck with a limited file write that isn’t so useful.

That turns out not to matter, because of how the server copies the header values. It copies each value using the exact length the client declares, which lets an attacker embed a null byte (\0) in the middle of the query-id. For example: .../some/target\0ignored. When the server later hands that path to the operating system to open the file, the OS treats the null byte as the end of the string and silently discards everything after it, including the server’s own result-…-.dat ending. The write lands on the exact path that preceded the null byte. Pointed at an existing file this overwrites it in place, keeping the original owner and permissions; a second variant uses two requests to create a brand-new file with an exact name. Because normal tools like curl and standard gRPC libraries restrict putting null bytes in headers, we must manually assemble the gRPC message to include our null byte.

Overwriting an existing file in place takes a single request whose metadata is:

query-id:     ../../../../../opt/charting/redishb.sh\0ignored
src-ip:       127.0.0.1
period-start: 0
period-end:   0

The Path to Code Execution

As with previous vulnerabilities we’ve reported that enable arbitrary file write, we’re looking for files on the filesystem that allow us to gain code execution by overwriting them. There’s a multitude of services that ingest files through cron jobs on the FortiSIEM. One file that is recurrently executed to perform health checks on the redis service is /opt/charting/redishb.sh. This script is invoked every 60 seconds by a cron job and is writable by the admin user context we have.

Putting it all together, to gain code execution we:

  1. Traverse the directory path
  2. Control the filename
  3. Overwrite a recurringly executed script 

Our proof of concept can be found on our GitHub.

Indicators of Compromise

We did not find any application logs that would explicitly reveal that this vulnerability was exploited. However, if the vulnerability is used to overwrite an existing script, one should carefully inspect the file write or modified timestamps, and inspect any that appear to not match the surrounding file timestamps.

Files of particular interest are:

  1. /opt/charting/redishb.sh
  2. /opt/phoenix/bin/phLicenseTool

Handing Pre-Contract FCI and CUI

red-team TrustedSec · 2026-10-20 · ↗ original

Contractors, subcontractors, and proposal consultants are often confused about their obligations regarding the safeguarding of Federal Contract Information (FCI) and Controlled Unclassified Information (CUI) received from the government as part of a request for proposals (RFP) or from another contractor in order to generate a quote as a subcontractor during the solicitation phase before a contract is signed.

The rollout of CMMC in Department of Defense (DoD) contracts has created more confusion as contractors have been incorrectly requiring their potential subcontractors and other organizations to demonstrate CMMC compliance to handle FCI and CUI before a contract is signed.

This post will help government contractors, subcontractors, and other organizations understand their FCI and CUI safeguarding obligations (or lack thereof) during the pre-contract solicitation phase by exploring:

  • The source of FCI and CUI protection obligations
  • How to handle FCI and CUI before a contract is signed
  • Common sources of confusion about pre-contract FCI and CUI
  • Why CMMC does not apply to FCI and CUI handled before a contract is signed

TrustedSec has years of experience helping contractors implement and assess themselves against the FAR 52.204-21 and NIST SP 800-171 requirements for safeguarding FCI and CUI and is a CMMC Registered Practitioner Organization (RPO). If you have FCI, CUI, NIST SP 800-171, and CMMC concerns, we are available to help—get in touch with us!

Special thanks to Brent Paris at Bid Designs for sharing information on the pre-contract issues his team commonly encounters while helping clients bid on government contracts that involve the handling of FCI and CUI.

Overview

  • The government’s standard contract clauses for safeguarding FCI and CUI do not apply during the solicitation phase.
    • The FAR 52.204-21, DFARS 252.204-7012, DFARS 252.204-7021 (CMMC), and other similar contract clauses never apply to FCI or CUI handled before a contract is signed or to FCI or CUI handled outside the specific contract that contains those clauses.
  • Contractors have no compliance obligations to safeguard FCI and CUI during the solicitation phase unless they have entered into a separate pre-contract agreement to do so.
    • Some contractors may receive FCI and CUI without any agreement in place and, as a result, have no compliance obligations whatsoever with regard to FCI and CUI.
  • Prime contractors that receive pre-contract agreements to safeguard FCI and CUI from the government must follow the requirements in those agreements.
    • Pre-contract agreements are not standardized the way the FAR and DFARS FCI and CUI safeguarding contract clauses are, so contractors will need to carefully review and understand the requirements of each individual agreement.
  • It is common for contractors that do not understand their (lack of) pre-contract FCI and CUI protection obligations to incorrectly push requirements, including FAR and DFARS clauses that should not apply, down to potential subcontractors and other organizations during the solicitation phase, thereby causing further confusion.
    • Organizations that subcontract for or otherwise work with government contractors should be aware of common points of confusion and be prepared to ask questions and push back with accurate information about the scope and applicability of FCI and CUI compliance obligations.

While confusion about the FCI and CUI programs has existed for a long time, the attention the CMMC program rollout is getting has significantly amplified the problem. The CMMC program is very well defined, but its scope and applicability are poorly understood by many contractors, and it has become common for contractors to incorrectly attempt to impose CMMC obligations on potential subcontractors and other organizations.

The Subcontractor Problem

This post focuses on how the government’s program for contractors handling FCI and CUI is supposed to operate, but there is a major problem that must be addressed up front: many large prime contractors are pushing supposed FCI and CUI compliance requirements (including CMMC) on their potential subcontractors that go above and beyond what is actually required by the government. Many of these requirements fall into the categories described in the Common Sources of Confusion section of this post.

In some cases, this may result from the prime contractor misunderstanding how the FCI and CUI programs are supposed to work, but it may also be an intentional, if misguided, attempt at avoiding liability for subcontractor non-compliance or a shortcut to avoid keeping track of which compliance obligations apply to each subcontractor.

This topic is explored further in our previous post A Vault With No Treasure - CMMC Level 2 Compliance for Subcontractors With No CUI, but for the purposes of this post, contractors should keep in mind that their upstream contractors may attempt to enforce requirements that are not part of the official government FCI and CUI programs. Whether or not subcontractors agree to or violate these non-standard requirements imposed by upstream contractors is a private contractual issue that has nothing to do with government penalties.

FCI and CUI Safeguarding Obligations

Contractors often misunderstand the source of FCI and CUI safeguarding obligations. The tangled mess of laws, regulations, government contract clauses, pre-contract agreements, flow-down requirements, and private contracts and agreements can be confusing, especially when contractors try to incorrectly apply various requirements on their subcontractors.

The subsections below untangle the true source of FCI and CUI safeguarding obligations to help understand what should apply to contractors and subcontractors.

Laws and Regulations

There are no laws or regulations that directly apply FCI or CUI safeguarding requirements to anyone outside the Federal government. The CUI regulation at 32 CFR Part 2002, a common source of confusion, only applies directly to executive branch agencies within the government itself, not to private-sector entities including government contractors. This is different from other regulations like ITAR, EAR, and HIPAA that automatically apply directly to private-sector entities.

Contractors and subcontractors are only obligated to safeguard FCI and CUI if they have agreed to do so via a specific agreement with the government as per 32 CFR 2002.1(f). The agreement is usually a clause in a contract or subcontract, but contractors may receive pre-contract agreements for the safeguarding of CUI if they are expected to review CUI to generate a quote during the solicitation phase.

Agreements are also specific to each solicitation or contract. A contractor or subcontractor that does not have a safeguarding agreement in place that covers a specific solicitation has no safeguarding obligations for the FCI and CUI received as part of that solicitation. This is true even if the contractor or subcontractor has previous agreements that contain FCI and/or CUI safeguarding clauses related to other solicitations or contracts.

Each document containing CUI must be protected in accordance with the requirements of the specific agreement it was received under because there is no single universal set of rules for contractors to safeguard CUI. CUI safeguarding requirements vary because:

  • Standard CUI protection clauses already in use by various agencies differ from each other.
  • Agencies revise their contract clauses from time to time.
  • Some contracts may require extra protection for certain categories of CUI.

Contract Clauses

The contract clauses for safeguarding FCI and CUI are standardized. The text of the clauses that the government inserts into contracts are contained in the Federal Acquisition Regulation (FAR) and agency-specific supplements, e.g., the DoD’s Defense Federal Acquisition Regulation Supplement (DFARS).

 There is currently no standard government-wide contract clause for safeguarding CUI, although one has been proposed. Contractors will only receive CUI safeguarding clauses in contracts if the agency they are working with has implemented the CUI program. More information on the proposed government-wide CUI clause is in our previous blog post CUI For the Rest of Us: The New Government-Wide CUI Protection Contract Clause.

 Common contract clauses related to FCI and CUI include:

These clauses only apply to information handled under a contract that contains these clauses. As a result, none of the requirements in these contract clauses apply to a contractor during the solicitation phase or to any other information handled outside a specific contract that contains these clauses. These contract clauses may be provided during the solicitation phase so contractors can understand what their obligations will be once a contract is signed, but do not take effect until the contract is awarded and signed.

Pre-Contract Agreements

Every government agency is supposed to have an agreement in place with parties outside the executive branch of government (including contractors) before sharing CUI as per the regulations that define how the government itself must handle CUI at 32 CFR 2002.4(c) and 32 CFR 2002.16(a)(5). This should be a formal written agreement but may be simple click-to-accept agreements on procurement sites like sam.gov or PIEE. The regulations also allow the government to make informal agreements that encourage, rather than require, the recipient to protect CUI.

As an example, an RFP posted on sam.gov for C-130 Depot Maintenance Repair and Overhaul at the time this post was written contains the following text related to CUI:

  • Solicitation documents may contain Controlled Unclassified Information (CUI)
  • Each potential Offeror shall certify that no dissemination of any export-controlled solicitation attachments and technical documents containing CUI subject to this requirement will occur in a manner that would violate applicable export control laws and regulations via submittal of their approved DD Form 2345.
  • Distribution of CUI by an Offeror to that Offeror’s team members, partners, subcontractors, suppliers and/or vendors shall be the responsibility of the Offeror and shall be limited to a “need to know” basis.
  • All guidance contained herein with regard to handling, distribution and destruction of CUI data shall be flowed down to all subcontractors and team members.

Neither these terms nor DD form 2345 impose detailed safeguarding requirements (e.g., NIST SP 800-171 or CMMC) on CUI shared as part of the RFP. The terms simply tell bidders they must only share CUI on a need-to-know basis and pass these same instructions to the people and organizations CUI is shared with. Potential contractors and subcontractors reviewing the CUI associated with this RFP would be under no obligation to be compliant with NIST SP 800-171 or have a CMMC status at any level.

Keep in mind that each pre-contract agreement is potentially unique, and this RFP was only used as an example of how vague pre-contract CUI agreements can be. Each agreement must be reviewed carefully to understand how contractors must handle pre-contract CUI under a specific RFP.

How to Handle Pre-Contract FCI and CUI

Determining how to handle FCI and/or CUI before a contract is signed depends on a few things:

  • Is CUI being handled?
  • Is a pre-contract agreement to protect CUI in place?
  • Are the pre-contract agreements official agreements flowed down from the government, or have they been created by other contractors?
  • Do other requirements apply to the data, whether or not it is FCI and/or CUI?

Each of these scenarios is covered in more detail in the following subsections.

Handling FCI Outside a Contract

Contractors have no obligation to safeguard FCI during the solicitation phase because FCI does not exist during the solicitation phase.

The definition of FCI at FAR 52.204-21(a) tells us that FCI is information provided by or generated for the government under a contract. This means FCI cannot exist unless there is a contract for it to exist under. A contract is not yet in place during the solicitation phase, therefore none of the information handled during the solicitation phase can ever be FCI.

Contractors should not attempt to enforce any pre-contract FCI safeguarding obligations on subcontractors because neither FCI nor FCI safeguarding obligations exist during the solicitation phase.

Handling CUI Under Pre-Contract Agreements

Contractors with a formal pre-contract agreement must safeguard CUI in accordance with the terms of that agreement. The requirements of pre-contract agreements will vary between agencies and may vary from contract to contract within a single agency, so it is important to keep track of which CUI is associated with which agreement to apply the correct safeguards.

Just because a contractor complies with contractual CUI safeguarding agreements, e.g., DFARS 252.204-7012 or DFARS 252.204-7021 (CMMC), does not mean it is compliant with pre-contract agreements. This topic is covered in more detail in the section on Common Sources of Confusion - Treating Compliance With Previous Contracts as a Safe Harbor below.

Some pre-contract agreements may include a requirement that the agreements be flowed down to potential subcontractors (as shown in the example pre-contract agreement above) while others may not. Flow-down requirements must be followed if they are included in pre-contract agreements.

A contractor should only flow down an official government pre-contract agreement associated with the solicitation it is seeking to subcontract. A pre-contract agreement from a different solicitation should never be flowed down as it would potentially impose incorrect compliance obligations, cause confusion, and/or unnecessarily deter potential subcontractors.

Handling CUI Without Agreements

As described above, a potential contractor or subcontractor that has not agreed to safeguard CUI is under no obligation to do so and may handle any CUI they receive however they like with no repercussions.

Government agencies have been inconsistent about sending formal CUI safeguarding agreements during the solicitation phase, so prime contractors should not be surprised if they receive CUI from the government without an agreement in place.

Potential subcontractors may also receive CUI from upstream contractors without a safeguarding agreement in place. This may be because:

  • The upstream contractor did not receive a CUI safeguarding agreement from the government so there’s nothing to flow down
  • The upstream contractor received a pre-contract agreement that did not contain a flow-down requirement
  • The upstream contractor didn’t understand that they were supposed to flow down the pre-contract agreement.

Contractors should never create their own pre-contract agreements for subcontractors as this will only cause confusion. Only legitimate pre-contract agreements from the government should be flowed down. If there is no legitimate agreement from the government, then CUI can be shared with potential subcontractors without an agreement in place.

Unofficial CUI Agreements

Contractors, especially large prime DoD contractors, have been causing much confusion by writing their own pre-contract CUI agreements and imposing requirements that do not align with the official government requirements for safeguarding CUI (sometimes even imposing CMMC certification requirements as a prerequisite to handle RFP material during the solicitation phase). These requirements are then sent to potential subcontractors as well as many other types of organizations that do not meet the government definition of subcontractor.

Ideally, a potential subcontractor (or any other organization besides a subcontractor) should be able to reach out to a contractor and inform them how their supposed pre-contract agreement does not align with the government’s requirements (link them to this blog post?). However, most subcontractors seem reluctant to push back on even the most nonsensical of requirements for fear of losing potential business to a competitor that will gladly say “yes” and will jump through the unnecessary extra hoops (or at least pretend to) just to win a deal.

Ultimately, it is up to each potential subcontractor to make their own decision as to whether they want to try to educate an upstream contractor on what sort of agreement would be appropriate, expend resources implementing compliance requirements that should not apply, or assume the risk of claiming to implement the supposed requirements without actually implementing them.

The next section of this post goes into more detail about the confusion that leads to and results from these nonsense clauses. More information on dubious CMMC requirements is also in our previous blog post The Proliferation of “Fake” CMMC Contract Clauses.

General Best Practices

Even if sharing information is allowed due to the lack of any formal agreements, some caution is advised to avoid unnecessary risks.

Basic principles to be considered include:

  • Are there private contractual agreements outside the FCI and CUI programs that apply (e.g., a non-disclosure agreement)?
  • Is there any implied confidentiality based on the context of a communication?
  • Is information sensitive for reasons unrelated to the FCI and/or CUI programs (e.g., export-controlled information, personal information, proprietary data)?
  • Is there a lawful government purpose for sharing information?

Organizations handling any potentially sensitive information should always do the following to protect themselves:

  • Treat information cautiously
  • Limit distribution and do not post potentially sensitive information publicly
  • Ask senders about expectations
  • Consider basic safeguarding even when it is not required

Common Sources of Confusion

Common sources of confusion related to pre-contract CUI (and sometimes CUI handling in general) include:

  • Directly applying CUI regulations to organizations that are not federal agencies
  • Applying contract clauses during the solicitation phase when no contract clauses should apply
  • Applying clauses from previous contracts to information handled under new solicitations and/or contracts
  • Treating compliance with previous contracts as a safe harbor instead of checking for compliance with new agreements
  • Treating proprietary or solicitation information as CUI
  • Incorrectly applying clauses to subcontracts that do not involve handling of CUI

Each of these is addressed in detail in the subsections below.

Directly Applying CUI Regulations

Contractors that come across the CUI regulations at 32 CFR Part 2002 often mistake it for a set of requirements that directly apply to contractors. Some contractors have incorrectly created their own CUI protection agreements based on these regulations and pushed them on potential subcontractors. Contractors have also confused subcontractors by incorrectly telling them that they must directly comply with 32 CFR Part 2002.

There is no such thing as 32 CFR Part 2002 compliance for any organization that is not a federal agency because 32 CFR 2002.1(f) explicitly tells us that:

  • These CUI regulations only apply directly to executive branch agencies.
  • Organizations outside the government (e.g., contractors) only become obligated to protect CUI via agreements with government agencies as described in 32 CFR 2002.4(c) and 32 CFR 2002.16(a).

Furthermore, CUI handling agreements do not impose a requirement to directly comply with the CUI regulations in 32 CFR 2002 but instead usually impose requirements related to NIST SP 800-171 as described in 32 CFR 2002.14(h)(2).

Effectively, the CUI regulations are almost irrelevant to contractors except as a source of information about what to expect from the government regarding CUI.

Contractors should never use the CUI regulations at 32 CFR Part 2002 as the foundation of their CUI protection program or CUI handling agreements, nor should contractors require their subcontractors or any other organizations such as proposal consultants to directly comply with these CUI regulations. Contractors should instead design their CUI compliance program around the requirements contained in their specific agreements with government agencies and flow only those same government agreements down to subcontractors.

Contractors have similarly attempted to incorrectly apply the CMMC regulation at 32 CFR Part 170 directly to subcontractors via their own home-made CUI protection agreements. This is explained in more detail in the CMMC Deep Dive below.

Applying Contract Clauses During the Solicitation Phase

Some contractors have attempted to incorrectly impose the requirements contained in the standard government FCI and CUI safeguarding contract clauses on subcontractors during the solicitation phase.

None of the standard FCI or CUI contract clauses apply before a contract is signed because that’s simply not how contracts work; contract clauses only come into effect once the contract that contains them is signed. FCI or CUI exchanged during the solicitation phase are not covered by potential future contract clauses. There are no FAR 52.204-21, DFARS 252.204-7012, or CMMC compliance obligations (just to pick a few examples) prior a contract or subcontract being signed.

Although contractors should inform potential subcontractors of the FCI and CUI safeguarding requirements that will be included in subcontracts, contractors should never try to impose the requirements contained in the safeguarding contract clauses on a subcontractor for CUI exchanged prior to a subcontract being signed. Only valid government pre-contract agreements should be applied to subcontractors during the solicitation phase.

Applying Clauses From Previous Contracts During the Solicitation Phase

Contractors may believe that they or their subcontractors are obligated to protect FCI and CUI received during the solicitation phase for a potential new contract because previous contracts contain FCI and/or CUI safeguarding clauses.

Once again, this is not how contracts work. The clauses in each contract only apply to the FCI and CUI received or created under that specific contract and create no safeguarding obligations for FCI or CUI outside of that specific contract, including CUI received as part of a solicitation for a new contract.

Contractors should never hold themselves or their subcontractors accountable for the safeguarding requirements in previous contracts when sharing information as part of a new solicitation. Only the pre-contract agreements related to the new solicitation apply to the potential contractor and subcontractors.

Treating Compliance With Previous Contracts as a Safe Harbor

Some contractors seem to be under the impression that subcontractors that have previously implemented contractual safeguards for the protection of FCI or CUI (e.g., DFARS 252.204-7012 or CMMC) are automatically compliant with any potential CUI safeguarding requirements in future pre-contract agreements. This results in contractors asking subcontractors if they are compliant with CUI safeguarding contract clauses and then flowing down CUI to potential subcontractors during the solicitation phase for a new contract without flowing down the pre-contract agreements for that specific solicitation.

There are many reasons why compliance with an existing CUI protection agreement, including the standard contract clauses, does not automatically indicate compliance with another CUI protection agreement:

  • Any given pre-contract agreement may contain different requirements than any other agreement, including the standard contractual agreements (e.g., some pre-contract agreements contain U.S. data residency requirements for CUI, as shown in the example from sam.gov above, while DFARS 252.204-7012 and CMMC do not).
  • Without flowing down the correct pre-contract agreement, subcontractor personnel will not be aware of the applicable requirements and may handle pre-contract CUI within systems that do not meet the safeguarding requirements.

This last point deserves some further explanation: Some contractors mistakenly believe that an entire contractor is either compliant or not compliant with CUI safeguarding requirements like CMMC. In reality, many contractors build isolated systems, e.g., a "CMMC Enclave", to exclusively handle information with specific safeguarding requirements to avoid applying these requirements to the rest of their environment. Subcontractors must be aware of pre-contract CUI agreements to understand which of their systems can effectively meet the requirements.

Contractors should never use compliance with prior CUI safeguarding agreements or contract clauses as an indication that subcontractors are compliant with the pre-contract or contract requirements of potential new contracts. Each government pre-contract agreement should be provided to potential subcontractors because each agreement is potentially unique.

Treating Proprietary or Solicitation Information as CUI

There are CUI categories for procurement and acquisition (PROCURE), source selection (SSEL), and proprietary business information (PROPIN). This causes some contractors to believe that information they create or share as part of a bid is CUI that must be marked and safeguarded by the contractor, and that any of this information provided to potential subcontractors must also be safeguarded by the subcontractor. This is not the case and is the result of a misunderstanding about how CUI is created and designated.

CUI is defined as information that the government itself is required to safeguard or control the dissemination of. The laws and regulations related to the CUI categories listed above only apply once the government receives the information from a contractor. Effectively, the CUI designation for these categories of information exists to protect the contractor from the government leaking their information to competitors and impose no obligations on the contractors that created the information as part of their bid.

Contractors are not obligated to safeguard their own proprietary or bid information as CUI simply because it will be provided to the government or a potential subcontractor. The contractor remains free to do whatever they want with their own information and share it with whomever they want.

Contractors should never attempt to impose CUI safeguarding requirements (including CMMC) on subcontractors simply because the subcontractor will be handling the contractor’s proprietary information or generating a bid. This information should instead be covered under normal non-disclosure agreements between private parties.

Subcontractors that are concerned that upstream contractors may be inappropriately marking information as CUI can review our previous post on Dealing With Unmarked and Mismarked CUI for more information and advice.

Incorrectly Applying Clauses

Some contractors have been warning subcontractors and other organizations of CUI safeguarding requirements during the solicitation phase when the recipient would never be subject to those requirements.

These supposed requirements often come in the form of screening questionnaires containing blanket demands for compliance with a long list of FAR and supplemental clauses in order to list the organization as an approved subcontractor or vendor. The blanket questionnaire approach overlooks a few facts:

  • CUI safeguarding requirements only apply to organizations that will handle CUI, many contracts and subcontracts do not involve CUI.
  • CUI safeguarding clauses from different government agencies often contain different requirements, for example:
    • Applying requirements to different scopes (only devices that directly handle CUI vs. devices that can connect to or provide security to devices that handle CUI)
    • Applying different requirements (NIST SP 800-171 revision 2 vs. revision 3)
    • Different compliance reporting requirements (third-party audit, self-assessment, or no reporting at all)
  • The specifics of CUI safeguarding requirements are potentially unique to each contract and subcontract based on the type of CUI involved, e.g., CMMC level and assessment requirements vary depending on the categories and quantity of CUI that will be handled under a specific contract.

Unnecessarily including every possible FCI and CUI requirement in every subcontract may result in a smaller pool of bids with higher prices as a result of the overhead of the additional imaginary requirements or subcontractors determining it is not feasible to meet such a long list of requirements.

Contractors have been observed attempting to incorrectly apply the requirements contained in the clauses to:

Organizations that are not subcontractors

  • FCI and CUI contract clauses only require flow-down to subcontractors.
    • Subcontractors (formally defined at 48 CFR 3.502-1) directly support the creation of government prime contract deliverables by furnishing supplies, material, equipment, or services that are necessary to the performance of a government contract.
    • Examples of organizations that would not be considered subcontractors include accounting firms, IT support, proposal consultants, etc. (unless the prime contract is for the provision of these services).
  • Contractors should never try to apply the FCI or CUI safeguarding clauses to any organization that does not meet the definition of a subcontractor.
    • CMMC contains requirements related to IT and cybersecurity service providers (described below) but do not required flow-down of the DFARS 252.204-7021 CMMC contract clause to these organizations.

Subcontractors that will not work on contracts for the relevant agency

  • Each agency that has implemented the CUI program has its own CUI safeguarding contract clause that only applies to contracts from that specific agency.
  • Subcontracts should never require compliance with a CUI safeguarding clause from any agency other than the agency responsible for the prime contract under which the subcontract is issued.
    • Compliance with DFARS 252.204-7012 and/or CMMC certification (both DoD-only requirements) is sometimes incorrectly requested from subcontractors that are bidding on subcontracts for agencies other than DoD.

Subcontractors that will not handle the type of information covered by the contract clause

  • FCI and CUI are two (2) different types of information with separate and distinct safeguarding requirements. Information that is export controlled under ITAR and EAR are also distinct from FCI and CUI.
  • Subcontracts should never require compliance with CUI safeguarding requirements if the subcontractor will not handle CUI as part of the subcontract, even if the prime contract involves handling CUI.
    • Compliance with DFARS 252.204-7012 or CMMC Level 2 is often incorrectly requested from subcontractors that will not handle CUI under the subcontract (DFARS 252.204-7012 and CMMC Level 2 clauses are only required to be passed down to subcontractors that will handle CUI).
  • Some categories of CUI are subject to extra safeguarding requirements beyond the standard safeguards applied to basic CUI.
    • Subcontracts should never require implementation of safeguards that do not apply to the categories of CUI that the subcontractor will handle, even if the prime contract involves handling of CUI categories with extra requirements.
  • Subcontracts often incorrectly require CMMC Level 2 C3PAO certification from subcontractors that will only handle CUI categories eligible for CMMC Level 2 self-assessment under the subcontract; only CUI in the CTI, DCRIT, NNPI, PSI, and DCNI categories requires C3PAO certification.

Contractors should pay close attention to the requirements of each solicitation and never try to flow down FCI and CUI requirements that do not apply based on the information that will be handled under a specific subcontract or to organizations that are not subcontractors.

CMMC Deep Dive

CMMC only applies to DoD contracts, so this information will be irrelevant to contractors and subcontractors that do not work with DoD contracts. More information on which organizations should expect to receive CMMC requirements is in our previous blog post CMMC NOPE: Why You Don’t Need to be CMMC Compliant.

As mentioned at the start of this post, CMMC does not apply to FCI and CUI handled during the solicitation phase. CMMC is purely a contractual requirement that only comes into effect once a contract is signed.

During the public comment period for the CMMC regulation, a commenter directly asked whether contractors must meet CMMC requirements during the solicitation phase, or to view RFPs that contain CUI. The government response is that “There are no CMMC requirements for reviewing FCI or CUI solicitation material.”

Unfortunately, there still seems to be much confusion about this. Contractors often send agreements that require subcontractors and other organizations to have CMMC certifications just to view solicitation materials, so it is apparently necessary to describe exactly how and why CMMC does not apply during the solicitation phase.

Directly Applying the CMMC Regulation

Some contractors have created their own subcontract clauses requiring compliance with the CMMC regulation itself (32 CFR Part 170), just as contractors have mistakenly tried to apply the 32 CFR Part 2002 CUI regulation directly to subcontractors as described above.

While the CMMC regulation contains the CMMC scope and requirements, the DFARS 252.204.7021 contract clause is the mechanism by which the DoD applies the CMMC regulation to contractors and is also the mechanism by which contractors are required to apply CMMC to subcontractors as per DFARS 252.204-7021(f)(1).

The main problem with a direct reference to the CMMC regulation is that the regulation does not tell contractors what CMMC level they must implement. The specific level requirement for each contract is inserted into the DFARS 252.204-7021 clause by DoD and is adjusted by contractors when the clause is flowed down in subcontracts. There are other important definitions and requirements in DFARS 252.204-7021 that would also be omitted when using a direct reference to the CMMC regulation instead.

Contractors should never include their own direct references to the CMMC regulation (32 CFR Part 170) in pre-contract agreements or subcontracts. Instead, contractors should flow down the following to potential subcontractors:

  • Any pre-contract agreements received from the government that contain flow-down requirements
  • The entire DFARS 252.204-7021 clause with the CMMC level requirement in paragraph (d)(1)(i) adjusted appropriately for the information that will be flowed down to the subcontractor as per the instructions in 32 CFR 170.23 only if the contractor itself received this clause in its contract

While not required, the contractor should also flow down:

  • All pre-contract agreements received from the government, even if they do not contain flow-down requirements
  • The DFARS 252.204-7025 solicitation provision warning of a CMMC requirement with the CMMC level requirement adjusted to match the potential DFARS 252.204-7021 clause

CMMC Clauses in Solicitations

DoD contractors will encounter the DFARS 252.204.7021 CMMC contract clause in solicitations, however, this does not impose pre-contract CMMC requirements. The text of the CMMC requirement at DFARS 252.204-7021(d)(1)(i) states that the contractor must have and maintain the correct CMMC status “for the duration of the contract” and says nothing about applicability during the solicitation phase (which occurs prior to, not within the duration of, a contract).

Contractors will also encounter the DFARS 252.204-7025 CMMC provision in solicitations. This does not impose any requirements during the solicitation phase and is only a warning that CMMC requirements will be in the contract.

Impact of Prior CMMC Contracts

CMMC clauses in contracts signed by a contractor also do not impose any obligations regarding FCI and CUI received as part of a later solicitation or contract. In general, the terms of any contract only apply to the information handled under that individual contract regardless of past or future contracts.

DFARS 252.204-7021(d)(1)(i) also states that the CMMC requirement only applies to “information systems used in performance of the contract, task order, or delivery order that process, store, or transmit FCI or CUI”. Information systems that are not being used in the performance of a specific contract, task order, or delivery order are therefore not in scope for CMMC (e.g., systems that exclusively handle FCI and CUI during the solicitation phase).

CMMC Subcontractor Requirements

As with contractors, CMMC does not apply to subcontractors during the solicitation phase.

Contractors will need to include the DFARS 252.204-7021 CMMC clause in subcontracts that will involve the handling of FCI and/or CUI, and it is strongly recommended that contractors warn any potential subcontractors of a potential future CMMC requirement, but this does not impose any CMMC requirements on the subcontractor until the subcontract with the CMMC clause is signed.

CMMC External Service Provider Requirements

ESPs that handle CUI and/or Security Protection Data (SPD) will be in scope for a contractor’s CMMC assessment, and contractors should verify that ESPs will be able to meet the applicable CMMC requirements.

Note that an ESP being in scope for CMMC as per 32 CFR 170.19(c)(2)(i) is different from a requirement to flow down CMMC contract clauses under DFARS 252.204-7021(f). The CMMC clause itself flows-down exclusively to subcontractors while the CMMC compliance of an ESP is a private contractual matter between the ESP and contractor. ESP compliance impacts the contractor’s CMMC compliance status without directly transferring CMMC compliance obligations to the ESP. Effectively, the contractor or subcontractor that uses an ESP is responsible for the ESP’s compliance, and if the ESP is not compliant, the contractor or subcontractor cannot be compliant either.

More information on how CMMC applies to the relationships between contractors, subcontractors, and ESPs is in our previous blog post CMMC Subcontractors and Service Providers.

CMMC Requirements for Organizations Other Than Subcontractors and External Service Providers

Contractors often send CMMC requirements to organizations that are neither subcontractors nor ESPs, perhaps as a result of not understanding how narrowly defined these two (2) categories are:

  • Subcontractors (formally defined at 48 CFR 3.502-1) directly support the creation of government prime contract deliverables by furnishing supplies, material, equipment, or services that are necessary to the performance of a government contract.
  • ESPs (formally defined at 32 CFR 170.4(b)) support the contractor's IT and/or cybersecurity operations with external people, technology, or facilities.

Any organization that does not meet either of these definitions, e.g., a consultant helping an organization formulate a response to a government RFP, should never receive CMMC requirements in a contract. Even if an organization falls under these definitions, any CMMC-related information passed on during the solicitation phase should only be a warning that a future contract will contain the CMMC requirements rather than attempting to impose CMMC obligations during the solicitation phase.

ConnectWise SkyKick Breach: How to Check Your Microsoft 365 Tenant

red-team SpecterOps · 2026-10-17 · ↗ original

An attacker used a compromised credential belonging to ConnectWise Cloud Backup (formerly SkyKick) to sign in to customers’ Microsoft 365 tenants. The credential belongs to the application itself, so the attacker inherited the permissions granted to it. Here’s what’s known so far and what to check in your own tenant. 

This blog will be updated and cross-linked as more information becomes available. 

tl;dr 

  • On October 15, an attacker used the ConnectWise Cloud Backup application’s credential to get Microsoft Graph tokens in customer tenants. 
  • As of October 19, Huntress has identified nearly 1,000 Entra tenants with sign-in activity from the IP address associated with the unauthorized activity (144.172.64[.]128), with approximately 300 of those sign-ins succeeding thus far.
  • Disable the affected ConnectWise applications now, and review every application in your tenant for credentials added since October 13. 

What happened in the ConnectWise SkyKick breach? 

On October 15, 2026, between 06:13 and 08:34 UTC, the ConnectWise Cloud Backup application signed in to customer tenants from 144.172.64[.]128, a hosting provider address. According to Huntress, which first broke the news of the breach, the attacker moved through tenants a few seconds apart, which points to a script working from a target list.  

According to The Hacker News, Microsoft is calling this an active supply chain attack, with the attackers likely abusing permissions customers had already granted the app, including Directory.ReadWrite.All.  

As of the publication of this blog, ConnectWise has shut off Cloud Backup application access while it investigates. The company says it has found no evidence that partner backup data was compromised. How the attacker obtained the credential has not been disclosed. 

Why doesn’t MFA stop this attack? 

MFA doesn’t apply because this is an application sign-in, so no user, device, or MFA prompt is involved. Backup tools need broad access to read and restore data. Anyone holding the app’s credential can reach the same mailboxes, OneDrive and SharePoint files, Teams data, and directory information the backup service can. 

In one tenant, Huntress also saw a second ConnectWise application grant itself Global Administrator and add new client secrets to two other trusted applications. That gives an attacker a way back in even after the original credential is reset.

How do I check if my Microsoft 365 tenant was affected? 

  1. Immediately disable application 506e08f9-6e9a-4da4-942b-a099a03644ae in the Entra admin center. Keep the apps disabled until ConnectWise confirms that all credentials have been reset. Tokens that were already issued can stay valid for up to 90 minutes after you disable an app.  
  1. Download the open-source version of AzureHound and run the collector. 
  1. Review your sign-in logs for service principal authentication tied to the application IDs listed above. Pay special attention to activity from the source IP 144.172.64[.]128. 
  1. Revoke unneeded application consents. If you don’t actively use SkyKick or ConnectWise Cloud Backup, remove their application consents from your tenant.
